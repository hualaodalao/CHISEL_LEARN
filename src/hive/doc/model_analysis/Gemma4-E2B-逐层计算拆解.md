# Google Gemma 4 E2B 逐层计算拆解

2026-10-29 ｜ 依据 `config.json`、权重清单（2,011 个张量，10,246,621,918 B）、`modeling_gemma4.py` 与 `configuration_gemma4.py` 源码核对

## 摘要

Gemma 4 E2B 是文本、视觉、音频三塔的端侧模型，仓库为 `google/gemma-4-E2B-it`。它有 35 层文本主干、20 层 KV 共享、每层一条 PLE 侧支，词表 262,144。参数必须分两本账看：台账 5,123,178,979，文本单 token 实际读取 2,279,768,099。两者相差 2,843,410,880，其中 82.6% 是一张只查一行的 PLE 表。

对芯片设计影响最大的几项：

- 台账参数 5,123,178,979，MXFP8 下 5.2820 GB；文本前向有效参数 2,279,768,099，2.3504 GB。差额定为"容量账减流量账"，不是精度误差。
- 单 token 计算 2,281,192,984 MAC，算术强度 0.9705 MAC/B。310 GB/s 下带宽上限 131.9 token/s；S=4096 时 127.9，S=32K 时 109.4，S=128K 时 73.0。
- PLE 表 2,348,810,240 参数，占台账 45.8%，但每 token 只取 8,960 个元素、17,920 B。若不做行选读而整表扫描，每 token 权重涨到 4.7915 GB，上限掉到 64.7 token/s，正好慢 2.04 倍。
- KV 共享把每 token 的 KV 从 43,008 B 压到 18,432 B，省 57.1%；S=128K 时容量从 5.637 GB 降到 2.416 GB。它省容量，不省每 token 的 KV 读取字节。
- MLP 占 68.27% 的 MAC，lm_head 占 17.65%。最后 20 层 MLP 宽度翻倍到 12,288，是 35 层里最大的结构性非线性。
- 全注意力只有 7 层，但 S=128K 时它们贡献 76.9% 的 MAC，单 token 总量涨到 9,863,388,416。滑动窗口 512 把另外 28 层钉死在常数开销。
- 视觉塔 540.83 GMAC、167.37 M 参数，MAC 是 Qwen3.5-0.8B 视觉塔的 6.64 倍；音频塔 221.28 GMAC、304.83 M 参数。一张 280 soft token 的图合计 1,080.68 GMAC。
- 内存拐点在 128K：台账权重 5.282 GB 加共享后 KV 2.416 GB 是 7.698 GB，8 GB 设备只剩 0.3 GB 余量；若按有效权重落盘则是 4.766 GB，6 GB 设备才成立。

# 第 1 章　事实基线

## 1.1 数据来源与核对方法

材料有四类：`https://hf-mirror.com/google/gemma-4-E2B-it` 上的 `config.json`；单文件权重 `model.safetensors` 的 header；`transformers` 主分支的 `modeling_gemma4.py`；以及同目录的 `configuration_gemma4.py` 与图像、音频处理器配置。Gemma 仓库是 gated，但镜像未登录即可读取 config 与 header，因此没有退到 Gemma 3n。

核对有两条独立路径。

第一条，header 元素数对文件字节。header 自身 263,952 B，文件总长 10,246,621,918 B，全 BF16。数据段 = 10,246,621,918 − 8 − 263,952 = 10,246,357,958 B，除以 2 得 5,123,178,979 个元素。header 里 2,011 个张量的元素数之和也是 5,123,178,979，差 0。文件头 8 B 加 header 263,952 B 是 263,960 B，占文件 0.0026%，这部分是 JSON 对齐与填充，不是漏算参数。

第二条，逐层求和对 header 分组。文本层 1,882,222,115，主 embedding 402,653,184，PLE 表 2,348,810,240，PLE 投影 13,762,560，两个 norm 1,792，视觉塔 167,365,056，音频塔 304,825,088，两个塔投影 3,538,944，合计 5,123,178,979。与 header 按前缀分组的结果逐位相等。

本文引用的源码语义有四处必须点名：`Gemma4TextMLP` 只在 `layer_idx >= num_hidden_layers - num_kv_shared_layers` 时用双宽；`Gemma4TextAttention` 在共享层不创建 `k_proj`、`v_proj`、`k_norm`，直接复用 `shared_kv_states`；`get_per_layer_inputs` 从 `[262144, 8960]` 的打包表里按 token 取一整行；`Gemma4ClippableLinear` 对输入和输出各做一次标量 clamp。这四句决定了后文所有账。

## 2.1 三个子模型

```
Gemma 4 E2B ─┬─ 文本主干 4,647,449,891 ─┬─ 12 × 滑动 base A      434,208,780
             │                          ├─ 3 × 全 base B          129,787,395
             │                          ├─ 16 × 滑动共享 As     1,031,929,872
             │                          ├─ 4 × 全共享 Bs         286,296,068
             │                          ├─ embed / lm_head        402,653,184
             │                          ├─ PLE 表              2,348,810,240
             │                          └─ PLE 投影 + norm        13,764,352
             ├─ 视觉塔   167,365,056 ─┬─ 16 × ViT block          151,046,592
             │                        ├─ patch 投影                 589,824
             │                        └─ 2D 位置表               15,728,640
             └─ 音频塔   304,825,088 ─┬─ 12 × Conformer block     302,163,936
                                      ├─ 下采样                   1,086,752
                                      └─ 输出投影                 1,574,400
```

三个子模型不是每次都同时出现。纯文本 decode 只读文本主干的 2,279,768,099 个有效参数；图像输入加读视觉塔与 768→1536 投影；音频输入加读音频塔与 1536→1536 投影；两者同时输入时三塔全开，但塔只在 prefill 阶段读一次，decode 阶段仍只读文本主干。

与 Qwen3.5-0.8B 的树相比，Gemma 多两个分支：PLE 表和音频塔。Qwen 的 MTP 头在 Gemma 里不存在，Gemma 也没有独立的投机头。

## 2.2 文本主干的层型配比

35 层按"4 滑动 + 1 全"的节奏排列，全层落在 4、9、14、19、24、29、34。第 15 层起进入 KV 共享区，同时 MLP 翻倍，两个变化共用同一个边界 `35 − 20 = 15`。

| 层型 | 层数 | 单层参数 | 合计 | 结构特征 |
|---|---:|---:|---:|---|
| A 滑动 base | 12 | 36,184,065 | 434,208,780 | 头维 256，MLP 6144，自带 K/V |
| B 全 base | 3 | 43,262,465 | 129,787,395 | 头维 512，MLP 6144，自带 K/V |
| As 滑动双宽共享 | 16 | 64,495,617 | 1,031,929,872 | 头维 256，MLP 12288，复用第 13 层 K/V |
| Bs 全双宽共享 | 4 | 71,574,017 | 286,296,068 | 头维 512，MLP 12288，复用第 14 层 K/V |
| **合计** | **35** | | **1,882,222,115** | |

比例是 12:3:16:4。前 15 层保留自己的 K/V，后 20 层只留 Q/O 与 MLP；省下来的容量用双宽 MLP 补回表示能力。这个交换是 Gemma 4 E2B 与 Qwen3.5-0.8B 最大的结构差异：Qwen 用 18 层线性递推算状态，Gemma 用 20 层共享 KV 省缓存，再给这 20 层加倍 MLP。

"每 5 层一个全注意力"的比例与 Qwen 的"每 4 层一个全注意力"接近，但 Gemma 的滑动层仍是标准 softmax，不是线性递推。所以 Gemma 没有跨 token 的 FP32 矩阵状态，SRAM 下限由 KV 与 MLP 中间激活决定，不由递推状态决定。

## 2.3 计算形态的四个类别

| 类别 | 本模型算子 | 单 token MAC 占比 | 硬件归属 |
|---|---|---:|---|
| GEMM / GEMV | 全部投影、MLP、PLE 投影、lm_head、塔内线性 | 98.7% | 矩阵引擎 |
| 归约 | RMSNorm、softmax、logit softcap、采样 | 0.5% | VPU |
| 逐元素 | GELU、残差、缩放、RoPE、clip | 0.8% | VPU |
| 串行递推 | 35 层依赖链、音频块内卷积、采样循环 | 不计 MAC | 控制 / VPU |
| 查表与搬运 | 主 embedding、PLE 行、KV cache、池化 | 0 MAC | DMA |

占比按 S=1 的 2,281,192,984 计算。GEMM 份额在短上下文接近 99%，到 S=128K 掉到 22.8%，因为 QKᵀ 与 AV 不属于 GEMM。这个反差是第 10 章分类矩阵的主线。

与 Qwen3.5-0.8B 对照：Qwen 有 18 层 DeltaNet 的串行递推，每层都有 16×128×128 的 FP32 状态；Gemma 没有这一类，四类里的"串行递推"只剩层间依赖和音频卷积。**不随模型缩放的是头几何与词表，不是层数**：Gemma 把 KV 头压到 1、头维抬到 256/512，KV 每 token 仍比 Qwen 高 54%。

## 3.2 层的通用骨架

一层文本层的 decode 骨架如下。所有层型共用这个拓扑，差别只在头维、K/V 是否存在、MLP 宽度。

```
x ──► [G0] RMSNorm ──► Q ──► q_norm ──► RoPE ─┐
        │                                      ├─► [G2] QKᵀ ──► softmax ──► AV ──► O ──► +x
        ├─► K ──► k_norm ──► RoPE ────────────┤                              [G3]
        └─► V ──► v_norm ─────────────────────┘
x' ──► [G4] RMSNorm ──► gate ─┐
        │              up ────┴─► GELU × ──► down ──► +x'
        │                                             │
        └──────────── [G5] PLE gate ──► × ple ──► proj ──► norm ──► + ──► × layer_scalar
```

读图约定只写这一次：`─►` 是有计算的依赖，`┄` 是纯视图、0 MAC，`═` 是跨 token 状态。`[G0]` 到 `[G5]` 是一层内的并行组。Q/K/V 三个投影在 G0 并行发射；QKᵀ、softmax、AV 在 G2 严格串行；O 投影与残差在 G3 汇合；MLP 的 gate/up 在 G4 并行，GELU 乘与 down 串行；PLE 在 G5 单独一条支路，活到层末。

三种形状变换贯穿全模型：

- 投影改宽度：Q 把 1536 投到 2048（滑动）或 4096（全），O 再投回 1536；MLP 把 1536 投到 6144 或 12288，再投回。
- 视图改分组：Q 的 2048 维拆成 8 头 × 256；K/V 的 256 维是 1 头 × 256。这一步 0 MAC，但决定后续 QKᵀ 的批量维。
- 残差保持宽度：所有残差都在 1536 维上做，包括 PLE 支路的最后一步。宽度不变意味着残差加法是纯逐元素，不占矩阵引擎。

### 3.3.3 关键路径与并行机会

关键路径是 A①→A②→A⑤→A⑧→A⑨→A⑩→A⑪→A⑫→A⑬→A⑭→A⑮→A⑯→A⑱→A⑲→A⑳→A㉑→A㉒→A㉔→A㉕→A㉖→A㉗。串行深度 18 级，但每级只有 1 个 token 的批量。真正的并行机会有三处：

- Q/K/V 三个投影共享 A① 的输出，可以合并成一次 [2560, 1536] 的 GEMV，权重拼接后 3.93 MB，一次发射。
- gate 与 up 共享 A⑮，可以合并成 [12288, 1536] 的 GEMV，一次读出 18.87 MB。
- PLE 支路只依赖 A㉑，与下一层的 A① 可以重叠；但下一层的 A① 依赖 A㉗，所以重叠窗口只有 PLE 的 0.79 M MAC，约占单层 2.2%。

B 与 A 的拓扑完全一样，只有九个尺寸差。全层头维 512，Q 为 4096 维，K/V 各 512 维；MLP 仍是 6144。

| 项 | A 滑动 | B 全 | 差值 |

| q_proj | 3,145,728 | 6,291,456 | +3,145,728 |
| k_proj | 393,216 | 786,432 | +393,216 |
| v_proj | 393,216 | 786,432 | +393,216 |
| o_proj | 3,145,728 | 6,291,456 | +3,145,728 |
| q_norm | 4,096 | 8,192 | +4,096 |

## 3.5 子模块 C：双宽 MLP（最后 20 层）

第 15 到 34 层的 MLP 宽度从 6144 翻到 12288。三个矩阵都翻倍：

| 张量 | 普通层 | 双宽层 | 增量 |
|---|---:|---:|---:|
| `gate_proj` | [6144, 1536] 9,437,184 | [12288, 1536] 18,874,368 | +9,437,184 |
| `up_proj` | [6144, 1536] 9,437,184 | [12288, 1536] 18,874,368 | +9,437,184 |
| `down_proj` | [1536, 6144] 9,437,184 | [1536, 12288] 18,874,368 | +9,437,184 |
| **小计** | **28,311,552** | **56,623,104** | **+28,311,552** |

双宽层每层 MLP MAC 是 56,635,392（含 GELU 12,288），普通层是 28,317,696。20 个双宽层合计 1,132,707,840 MAC，15 个普通层合计 424,765,440，MLP 总量 1,557,473,280，占单 token 的 68.27%。

双宽 MLP 的中间激活是 12288 × 2 B = 24.6 KB，是普通层的两倍。这个数不随上下文变，但决定单层的 SRAM 驻留下限。Qwen3.5-0.8B 的 MLP 中间宽度是 3584，只有 Gemma 双宽层的 29.2%；这是 Gemma 单 token MAC 是 Qwen 2.97 倍的主要原因之一。

## 3.6 层型 D：PLE 侧支（35 层，每层一份）

PLE 不是一层，而是挂在每一层末尾的侧支。它解决的是"小模型容量不够"的问题：主 hidden 只有 1536，但每个 token 额外带 35 × 256 的查表向量，给每层一份 256 维条件。

```
input_ids[1] ──► PLE 表行 [1,8960] ──► ×16 ──► [1,35,256]
                                                   │
inputs_embeds[1,1536] ──► per_layer_model_projection [8960,1536] ──► ×1/sqrt(1536)
                                                   │
                                          每层取 [1,256] ──► ple_i
                                                   │
第 i 层隐藏 x[1,1536] ──► gate [256,1536] ──► GELU ──► × ple_i ──► proj [1536,256] ──► RMSNorm ──► + x
```

打包表 `[262144, 8960]` 的 8960 维就是 35 × 256。查表本身 0 MAC，但每 token 要读 8960 × 2 B = 17,920 B。全模型投影 `[8960, 1536]` 每 token 13,762,560 MAC、14.19 MB 权重；它把 8960 维压回 1536 维，再按层切片。

每层的 PLE 支路是 791,296 MAC：gate 393,216、激活 256、回投 393,216、norm 3,072、加 1,536。35 层合计 27,695,360 MAC，占单 token 的 1.21%。

PLE 的关键数字不是 MAC，是容量与流量的分离：

| 项 | 数值 | 说明 |
|---|---:|---|
| 表参数 | 2,348,810,240 | 262144 × 8960 |
| 表字节（MXFP8） | 2.4216 GB | 占台账 45.8% |
| 每 token 读取 | 17,920 B | 一行 8960 个 BF16 |
| 每 token 有效参数 | 8,960 | 只算当前行 |
| 未读比例 | 99.9996% | 262,143 / 262,144 行不读 |
| 全表扫描的每 token 流量 | 2.4216 GB | 若不做行选读 |
| 全表扫描的带宽上限 | 58.7 token/s | 5.2820 GB 全读 |

PLE 的精度也特殊：查表后乘 `sqrt(256)=16`，全模型投影后乘 `1/sqrt(1536)=0.0255`，每层合并后再乘 `1/sqrt(2)=0.7071`。三个缩放都是常数，可以在量化时折进 scale，不增加运行时乘法。

## 3.7 机制 E：KV 共享（20 层）

第 15 层起，20 层不再计算 K/V。滑动共享层复用第 13 层的 K/V，全共享层复用第 14 层的 K/V。建模代码里 `shared_kv_states` 是一个按层型索引的字典，只有两个条目：`sliding_attention` 与 `full_attention`。

```
层 0..12  滑动 base：各自写 K/V ───────────────┐
层 13     滑动 base：写 K/V，并标记 full_length ├─► 共享给层 15..34 的 16 个滑动层
层 14     全 base：写 K/V，并标记 full_length ──┴─► 共享给层 19..34 的 4 个全层
层 15..34 共享层：只算 Q，K/V 从上面两个条目读
```

共享后缓存套数是 15，不是 35：12 个滑动 base 加 3 个全 base。每 token 的 KV 字节：

- 共享前：28 × 1 × 256 × 2 × 2 + 7 × 1 × 512 × 2 × 2 = 28,672 + 14,336 = 43,008 B。
- 共享后：12 × 1 × 256 × 2 × 2 + 3 × 1 × 512 × 2 × 2 = 12,288 + 6,144 = 18,432 B。
- 节省：24,576 B/token，57.1%。

共享层在计算上省掉 K/V 投影与 k_norm/v_norm：滑动共享层每层 787,456 MAC，全共享层每层 1,574,912 MAC，20 层合计 18,898,944 MAC，占单 token 的 0.83%。它不省注意力的 QKᵀ 与 AV，因为共享层仍要用共享 K/V 做完整的窗口注意力。

checkpoint 仍为 20 个共享层保留 k/v 与 k_norm，共 18,880,512 参数。这些权重在建模代码里从未被实例化，属于"台账有、流量无"的死权重。它们和 PLE 未读行一起构成 2.843 B 的差额。

# 第 5 章　通用算子库

## 5.1 RMSNorm

形状：输入 `[1, N]`，权重 `[N]`；文本层 N=1536，q_norm 的 N=256 或 512，v_norm 无权重。

公式：`y = x / sqrt(mean(x²) + eps) × w`，`eps=1e-6`。内部先把 x 转 FP32，归一化后再乘 weight，最后转回 BF16。

MAC：`2N`（平方和归约 N 次乘加，缩放 N 次）。文本层每次 3,072，q_norm 每次 4,096（8 头 × 256），k_norm 与 v_norm 各 512。

精度要求：归约必须 FP32。1536 维 BF16 累加的相对误差约 2⁻⁸，在 35 层里会累积成可见漂移；FP32 累加后误差回到 2⁻²³ 量级。weight 可以 BF16。

实现坑：`mean` 的分母是 N 而不是 N−1；`eps` 加在均值里面而不是根号外；v_norm 的 `with_scale=False`，如果实现按有 weight 处理会读到不存在的张量。Gemma 的 weight 初始化是全 1，不是零，不能省掉乘法。

## 5.2 GELU（tanh 近似）

形状：`[1, 6144]` 或 `[1, 12288]`。

公式：`0.5x(1 + tanh(sqrt(2/π)(x + 0.044715x³)))`。

MAC：本口径按每元素 1 MAC 计，文本普通层 6,144，双宽层 12,288。实际 tanh 在 VPU 上约 8–12 个周期/元素，是账面值的 8–12 倍；它不在矩阵引擎上，不能用 MAC 直接折算时间。

精度要求：输入 BF16，tanh 内部 FP32，输出 BF16。x³ 项在 12288 宽上容易溢出 BF16 的动态范围，必须先转 FP32。

实现坑：Gemma 用 `gelu_pytorch_tanh`，不是 `silu`，也不是 erf 版本；三者数值差在 1e-3 量级，量化后会放大。gate 与 up 的乘法要在 GELU 之后做，顺序反了结果不同。

## 5.3 RoPE（两套）

形状：Q `[1, 8, 256]` 或 `[1, 8, 512]`，K `[1, 1, 256]` 或 `[1, 1, 512]`。

公式：对每一对 `(x_{2i}, x_{2i+1})` 做 `x' = x cos θ_i + rot(x) sin θ_i`，`θ_i = pos / 10000^(2i/d)`。

两套参数必须分开实现：

| 层型 | 旋转维 | theta | 位置范围 | 每层 MAC |
|---|---:|---:|---|---:|
| 滑动 | 256（全维） | 10,000 | 0–511 窗口 | 4,096 |
| 全 | 128（512 的 25%） | 1,000,000 | 0–131071 | 2,048 |

精度要求：cos/sin 表 FP32，乘加 FP32，输出 BF16。全层的 theta 是 1e6，滑动层是 1e4，不能共用一张表。

实现坑：proportional RoPE 只旋转前 128 维，后 384 维原样通过；把 512 维全转会改变模型输出。滑动层的窗口位置是全局位置还是窗口内相对位置，必须与训练一致；Gemma 用全局位置，窗口只影响可见范围。RoPE 在 q_norm/k_norm 之后做，顺序不能换。

## 5.4 Softmax 与 logit softcap

形状：注意力分数 `[8, 1, S]`；输出 logits `[1, 262144]`。

公式：`p = exp(s − max) / sum(exp(s − max))`；输出头 `logits = 30 × tanh(logits / 30)`。

MAC：注意力 softmax 按每头 1 MAC 计，S=1 时 8；这是账面低估，实际 exp 与归约在 VPU 上约 3–5 个周期/元素。softcap 是 262,144 个元素各一次 tanh，约 0.26 M MAC 当量。

精度要求：分数 FP32，max 与 sum FP32，概率 BF16 送回 AV。softcap 必须在 FP32 里做，BF16 的 tanh 在 30 附近分辨率不足。

实现坑：滑动层只对窗口内 512 个分数做 softmax，窗口外是 −∞ 而不是 0；全层对 131072 个分数做，掩码要按位置生成。softcap 在 lm_head 之后、采样之前，顺序反了会改变 top-k 分布。

## 5.5 裁剪线性（视觉与音频）

形状：视觉 `[2520, 768]`，音频 `[750, 1024]`；权重与普通线性相同。

公式：`y = clamp(W · clamp(x, in_min, in_max) + b, out_min, out_max)`。

MAC：线性本身的 MAC 与普通线性相同；裁剪是每元素 2 次比较，视觉每层约 `N × (11×768 + 3×3072)` 个比较点，音频每层约 `S × (9×1024 + 4×4096)`。

精度要求：clamp 标量 FP32，输入输出 BF16。视觉第 0 层的 `input_max=2.630859375`、`output_max=2.5703125`；每个裁剪线性有四个标量（输入上下、输出上下），每层 7 个裁剪线性共 28 个标量。

实现坑：clamp 必须在量化前后各一次，不能只做一次；标量是按层训练的，不是全局常数；把 clamp 折进量化 scale 会改变饱和点。

## 5.6 音频相对注意力与轻卷积

形状：音频 750 帧，8 头 × 128；块内 12 个 query，左上下文 13，右 0。

公式：`score = q kᵀ + q rᵀ`，`r` 是相对位置 key；`y = softmax(score / sqrt(128)) v`；`softcap=50`。

MAC：每层 QK 18,579,456、AV 18,579,456、相对 key 投影 13,631,488。轻卷积 `linear_start` 把 1024 投到 2048，深度卷积核 5，`linear_end` 投回 1024，合计 2,363,136,000 MAC/层。

精度要求：相对 key FP32 生成，注意力分数 FP32，softcap 50 在 FP32 里做。

实现坑：音频是分块因果，不是全因果；块内 12 帧、左 13 帧的掩码是固定的，不能按文本的三角掩码处理。轻卷积的残差权重是 0.5，不是 1.0。

### 6.1.4 实现与测试坑（按危害排序）

1. 共享层权重仍在 checkpoint。按名字全量加载会把 18.88 M 死权重读进 DRAM；如果推理框架不跳过，每 token 多读 19.5 MB，带宽上限从 131.9 掉到 130.8。
2. PLE 行不是连续 35 段。8960 维一行里 35 个 256 维块连续存放，但每层只取自己那块；DMA 要按 512 B 粒度切 35 次，不能假设整行一次进 SRAM。
3. PLE 投影的 `1/sqrt(1536)` 缩放容易漏。漏掉后 PLE 支路输出大 39 倍，层输出饱和。
4. `layer_scalar` 不是 1。第 0 层是 1.142578125；35 层各有自己的值，不能共用一个常数。
5. v_norm 无 weight。实现若按有 weight 的 RMSNorm 调用，会读到不存在的张量或把 v 清零。
6. q_norm 是每头 256 维，k_norm 是每 KV 头 256 维；权重形状是 [256]，不是 [8,256]。
7. 全层头维 512，滑动层 256；同一个 attention kernel 不能写死 256。
8. 滑动窗口 512 的边界是闭区间还是半开区间，差一个 token 就会让第 513 个位置的结果变化。
9. 全层 RoPE 只转 128 维，theta 1e6；与滑动层的 256 维、theta 1e4 混用会让长上下文位置错位。
10. softcap 30 在采样前，不在 lm_head 的 GEMM 里；把它折进权重会改变 top-k。

全模型 7 个全层（3 个 base + 4 个共享）在共享后只存 3 套，所以 128K 的全层 KV 是 3 × 268,435,456 = 805,306,368 B。滑动层 12 套各 512 × 1,024 = 524,288 B，合计 6,291,456 B。按环形缓冲实际驻留 811,597,824 B（0.8116 GB），全层占 99.2%，滑动占 0.8%；若统一按 128K 全上下文分配（8.3 表口径），总计 2,415,919,104 B，全层占 33.3%，滑动名义占 66.7%。

### 6.2.4 引擎准入

B 与 A 相同，只有两点不同：全层的 QKᵀ/AV 在 S=1 时仍是 4,096 MAC，但 K 维是 512，点积更长；RoPE 只转 128 维，VPU 的三角表更短。全层的 Q/O 投影 K=1536、N=4096，是单层最大的两个 GEMV，各 6.29 M MAC。

| 算子 | 能否上引擎 | 原因 |
|---|---|---|
| Q/O 投影 | 能 | N=4096，K=1536 |
| K/V 投影 | 能 | N=512，K=1536 |
| QKᵀ / AV | 能但低效 | S=1，N=8 头 |
| softmax / norm / RoPE | 不能 | 归约或逐元素 |

### 6.2.5 十个必须记住的坑

1. 全层头维 512，Q 是 4096 维；把它当 8×256 处理会少一半。
2. 全层 RoPE 是 proportional，只转 128 维，theta 1e6。
3. 全层 K/V 各 512 维，k_norm 权重是 [512]。
4. 全层只在 4、9、14、19、24、29、34 出现，共 7 层。
5. 共享的全层复用第 14 层 K/V，不是第 13 层。
6. 共享后全层只剩 3 套 KV cache，不是 7 套。
7. 全层注意力的分数矩阵在 128K 时是 8 × 131072，不能整块驻留 SRAM。
8. 全层没有滑动窗口，掩码是全三角。
9. 全层 O 投影的输入是 8×512=4096 维，不是 2048。
10. 全层的 `layer_scalar` 与滑动层不同，不能共用。

### 6.2.6 与其它章节的接口

本节被直接引用的数字有：单层 B MAC 43,305,224（8.1）、单层权重 44.60 MB（8.2）、KV 2,048 B/token（8.3）、全层 128K 单 token 1,073,741,824 MAC（8.1）、3 套全层 cache 805,306,368 B（8.3）。第 9 章的 decode 时间线把 B 归入“基础 15 层”一组，第 10 章把它归入“全注意力”一类。

双宽 MLP 只改宽度，不改拓扑。gate 与 up 都是 [12288, 1536]，down 是 [1536, 12288]。单层 56,623,104 参数，56,635,392 MAC。

| 35 层 gate | [1,1536]×[256,1536] | 13,762,560 | 13.76 MB | 引擎 |
| 35 层激活 | [1,256] × 35 | 8,960 | 0 | VPU |
| 35 层乘 ple | [1,256] × 35 | 0 | 0 | 融合 |

引擎准入：gate 与回投能上引擎（K=1536 与 256），查表只能 DMA，激活与 norm 在 VPU。精度：表 MXFP8 按行 scale，投影 MXFP8 按列 scale，gate/回投 MXFP8，norm FP32。

坑：

1. 8960 维行里 35 个 256 维块的顺序必须与层号一致；错一块，35 层全错。
2. 表缩放 `sqrt(256)=16` 和投影缩放 `1/sqrt(1536)=0.0255` 不能互换。
3. PLE 表按 token id 随机命中，row gather 的 DRAM 行激活开销远大于 17,920 B 的有效载荷；连续 token 的 id 不连续时，实际带宽可能是有效值的 2–4 倍。
4. 表 MXFP8 的 32 元素块跨 256 维边界时，行 scale 要对齐到 256，不能按 32 切。
5. PLE 支路在 MLP 之后，不能提前到 attention 之前；提前会改变残差流。

## 6.5 机制 E：KV 共享

共享的缓存结构：

| 层型 | base 层 | 共享层 | 头维 | 每 token 每套 | 套数 | 合计/token |
|---|---:|---:|---:|---:|---:|---:|
| 滑动 | 12 | 16 | 256 | 1,024 B | 12 | 12,288 B |
| 全 | 3 | 4 | 512 | 2,048 B | 3 | 6,144 B |
| **合计** | **15** | **20** | | | **15** | **18,432 B** |

共享前是 35 套（28 滑动 + 7 全），43,008 B/token。共享后 15 套，18,432 B/token。节省 24,576 B/token，57.1%。

计算节省：每个共享层省 k_proj、v_proj、k_norm 与 v_norm。滑动共享层每层省 787,456 MAC，全共享层每层省 1,574,912 MAC。16 × 787,456 + 4 × 1,574,912 = 12,599,296 + 6,299,648 = 18,898,944 MAC，占单 token 的 0.83%。

共享的代价是依赖：第 15 层必须等第 13 层算完 K/V，第 19 层必须等第 14 层。prefill 时这会把 35 层的流水切成两段，前 15 层必须先完成；decode 时只影响首 token。

坑：

1. 共享 key 是层型，不是层号；滑动共享层读 `sliding_attention` 条目，全共享层读 `full_attention`。
2. 只有第 13、14 层写 cache；第 15–34 层不能重复写，否则缓存翻倍。
3. 滑动共享 cache 只需要 512 长度，全共享 cache 需要 131072；两者不能共用同一个 ring buffer 大小。
4. 共享层的 Q 仍要按自己的位置做 RoPE，不能复用 base 层的 Q。
5. 量化时共享 cache 必须与 base 层同 dtype，不能 base 用 BF16、共享层读 FP8。

# 第 7 章　视觉塔、音频塔与输出头

## 7.1 视觉塔结构

视觉塔是 16 层双向 ViT，宽 768，12 头 × 64，MLP 3072。输入按 16×16 patch 切开，最多 2520 个 patch；3×3 池化后得到 280 个 soft token，再过 768→1536 投影进入文本主干。

```
图像 ─► patch 16×16 ─► 2520 token ─► patch 投影 [768,768] + 2D 位置表
     ─► 16 × block（双向注意力，无因果掩码）
     ─► 3×3 池化 ─► 280 token ─► 768→1536 投影 ─► 文本主干
```

与 Qwen3.5-0.8B 的视觉塔相比，Gemma 的层数多 4 层、宽度相同，但 patch 数从 2304 涨到 2520，且注意力是 2520² 的全双向，不是分块或窗口。Qwen 的视觉塔 81.44 GMAC，Gemma 是 540.83 GMAC，6.64 倍。

N=2520，M=280，16 个 block，12 头 × 64。

| V③ | QKᵀ | 16 × 12 × [2520,2520] × 64 | 78,033,715,200 | 引擎 |

- V⑧：16 × 2 × 2520 × 768 = 61,931,520。注意力后与 MLP 后各一次。
- V⑨：16 × 12 × 32 × 4 × 2520 = 61,931,520。32 是旋转对数，4 是每对乘加。

## 7.3 视觉塔的成本

| 类别 | MAC | 占比 |
|---|---:|---:|
| patch 投影与位置 | 1,492,162,560 | 0.28% |
| 四个线性投影 | 95,126,814,720 | 17.59% |
| 注意力（QKᵀ + softmax + AV） | 157,286,707,200 | 29.08% |
| MLP | 285,380,444,160 | 52.77% |
| norm、GELU、残差、RoPE | 495,452,160 | 0.09% |
| 裁剪开销 | 712,212,480 | 0.13% |
| 池化与 merger | 2,150,400 | 0.00% |
| 768→1536 投影 | 330,301,440 | 0.06% |
| **合计** | **540,826,245,120** | **100.0%** |

总 GMAC 540.83，GFLOP 1,081.65。视觉路径权重 168,544,704（含投影），MXFP8 下 173.77 MB；算术强度 540.83e9 / 173.77e6 = 3,112 MAC/B，是文本 0.9705 的 3,207 倍。视觉塔是纯算力负载，不是带宽负载。

等价文本 token 数：540.83 / 1.9266 = 280.7。**视觉塔的计算量恰好等于把 280 个 soft token 再过一遍文本主干**，所以一张图的成本约等于 561 个文本 token。

分辨率翻倍的算例。patch 数从 2520 涨到 5040，线性项 ×2、注意力项 ×4：

| patch 数 | soft token | 线性项 GMAC | 注意力项 GMAC | 总 GMAC | 倍数 |
|---:|---:|---:|---:|---:|---:|
| 2520 | 280 | 383.54 | 157.29 | 540.83 | 1.00 |
| 5040 | 560 | 766.74 | 629.15 | 1,395.89 | 2.58 |
| 10080 | 1120 | 1,533.16 | 2,516.59 | 4,049.75 | 7.49 |

线性项 = 总 − 注意力项；翻倍时 patch/投影/MLP/裁剪都 ×2。4 倍 patch 时总成本 7.49 倍，注意力项从 29.08% 涨到 62.1%。这就是为什么视觉塔不能按"图像边长线性"估时。

## 7.4 视觉塔的矩阵引擎映射

- 算力时间：540.83 GMAC / 12.5 TMAC/s = 43.3 ms。
- 带宽时间：173.77 MB / 310 GB/s = 0.56 ms。
- 失衡比：77.3 倍，纯算力受限。

结论：视觉塔的量化优先级高于文本。把 768×768 与 768×3072 的权重从 MXFP8 降到 INT8，线性部分占 70.9%，时间可从 43.3 ms 降到 28.0 ms；但 V③/V⑤ 的 QKᵀ 与 AV 在 2520² 上占 29.08%，它们需要 INT8 点积或 FP8 累加。只有注意力也量化，总时间才降到 21.6 ms；注意力单独跑仍需 12.6 ms。

## 7.5 视觉塔的坑（速查）

1. 漏乘 block 数 16：单 block 33.69 GMAC，漏乘后总账少 16 倍。
2. 漏乘头数 12：QKᵀ 与 AV 各少 12 倍。
3. 池化 M 用 patch 数 2520 而不是 280：merger 与投影高估 9 倍。
4. 位置表是 2 × 10240 × 768，不是 2520 × 768；多出来的 7720 行是为更大图像预留。
5. 视觉注意力是双向的，没有因果掩码；按文本三角掩码算会少一半 QKᵀ。
6. 裁剪线性有 7 个/block，每个 4 个标量，共 28 个/block、448 个/塔。
7. 3×3 池化的窗口不重叠，280 = 2520 / 9，除不尽时要补边。
8. 768→1536 投影只作用在 280 个 soft token 上，不作用在 2520 个 patch 上。
9. 视觉塔的 RoPE 是 2D，theta 100，不是文本的 1e4/1e6。
10. 图像 token 进入文本主干后按普通 token 计费，280 个 token 的 prefill 成本要单独加。

## 7.6 输出头与采样

输出头与主 embedding 共享，形状 [262144, 1536]。单 token MAC 402,653,184，MXFP8 权重 415.13 MB，logits 缓冲 262144 × 2 B = 524,288 B。它在 decode 里是最大的单算子，占 17.65% MAC 与 17.66% 权重流量。

softcap：`logits = 30 × tanh(logits / 30)`，262,144 个元素各一次 tanh，约 0.26 M MAC 当量。它必须在采样前做，且必须在 FP32 里做。

采样参数是 top_k=64、top_p=0.95。按 25 GOPS 的 VPU、每次比较 1 个操作估算：

| 方法 | 比较/操作数 | 时间 | 占 7.58 ms 预算 |
|---|---:|---:|---:|
| argmax | 262,144 | 0.010 ms | 0.14% |
| top-k 64（堆） | 262,144 + 64×18 = 263,296 | 0.011 ms | 0.14% |
| top-p 0.95（在 64 内） | 64×6 + 64 = 448 | 0.00002 ms | 0.00% |
| 全排序 | 262,144×18 = 4,718,592 | 0.189 ms | 2.49% |

结论：top-k 64 的采样开销可以忽略，全排序也不到 3%。词表 262,144 的主要成本在 lm_head 的 415.13 MB 权重，不在采样。Qwen3.5-0.8B 的词表 248,320，lm_head 占带宽 33.8%；Gemma 的词表只大 5.6%，但文本总流量大 3.03 倍，lm_head 占比反而降到 17.66%。

## 7.9 多模态的坑

1. 视觉塔与音频塔只在 prefill 读一次权重，decode 不读；把它们算进每 token 带宽会把 2.35 GB 高估到 2.84 GB。
2. 280 个视觉 token 进入文本后，文本 prefill 的 S=280，不是 2520；注意力按 280 算。
3. 音频 750 token 是 30 s，40 ms/token；不足 30 s 要补零或截断，token 数按帧算不是按秒四舍五入。
4. 音频块内 12 query、左 13 上下文，掩码是固定块结构，不是全三角。
5. 视觉与音频可以同时输入，两个塔的权重都读，但文本只跑一次；总算力是两塔相加加文本。
6. 视觉裁剪标量 448 个、音频 432 个，量化时必须逐层保留，不能用一个全局 clamp。
7. 视觉位置表 10240 行，最大 patch 2520，剩余 7720 行是预留；不要按表大小估 patch 数。
8. 音频输出投影 1024→1536 与视觉 768→1536 是两套权重，不能共用。
9. logits softcap 30 对多模态输出同样生效，不能只在纯文本路径加。
10. 图像 token 的 embedding 已在视觉塔里乘过 768→1536 投影，进入文本后不再乘主 embedding 的 sqrt(1536)。

KV 共享前后逐档对照。容量列按"每层都保留全上下文"计，是分配上界；滑动层实际只需 512 长度的环形缓冲，按环形缓冲的驻留量在表后单列。

| S | 共享前 B/token | 共享后 B/token | 省 B/token | 共享前容量 | 共享后容量 | 省容量 | 每 token 读取 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 4,096 | 43,008 | 18,432 | 24,576 | 176.2 MB | 75.5 MB | 100.7 MB | 73.4 MB |
| 32,768 | 43,008 | 18,432 | 24,576 | 1,409.3 MB | 604.0 MB | 805.3 MB | 484.4 MB |
| 131,072 | 43,008 | 18,432 | 24,576 | 5,637.1 MB | 2,415.9 MB | 3,221.2 MB | 1,893.7 MB |

"每 token 读取"比容量小，因为 28 个滑动层只读最近 512 个 token：28 × 512 × 1,024 = 14,680,064 B；7 个全层读全上下文：7 × S × 2,048。S=128K 时 7 × 131072 × 2048 = 1,879,048,192 B，加滑动层 14,680,064 B，合计 1,893,728,256 B。读取按 28 个消费层各读一次计，不假设共享 cache 在 SRAM 命中。容量是 2,415,919,104 B，读取是 1,893.7 MB，差值来自滑动层只保留 512 长度。

权重加 KV 的常驻账：

| 口径 | 权重 | KV（128K） | 合计 | 8 GB 余量 | 6 GB 可行性 |
|---|---:|---:|---:|---:|---|
| 台账 | 5.2820 GB | 2.4159 GB | 7.6979 GB | 0.30 GB | 不可行 |
| 有效 | 2.3504 GB | 2.4159 GB | 4.7663 GB | 3.23 GB | 可行 |

余量按全上下文分配上界计；若滑动层用环形缓冲（0.8116 GB），台账与有效两种口径的 8 GB 余量分别为 1.91 GB 与 4.84 GB。6 GB 下有效口径可行，台账口径即使环形缓冲也要 6.0936 GB，仍差 0.09 GB。

必须做的设计决策：

- KV 用 FP8。18,432 B/token 减半到 9,216 B/token，S=4K 省 37.7 MB，32K 省 302.0 MB，128K 省 1.208 GB。代价是共享 cache 必须与 base 层同 dtype，不能部分层 BF16。
- PLE 表常驻 MXFP8。2.4216 GB 占台账 45.85%，若为了省容量把它放 DRAM 外面，每 token 的 17,920 B 行读会变成随机远距访问，延迟不可控。
- 选择性落盘。若设备只有 6 GB，必须只物化文本有效权重 2.3504 GB，再按语言/词表裁剪 PLE 行；全量台账加 KV 的 7.6979 GB 放不进 6 GB。
- 滑动窗口 512 是容量杠杆。28 层只需 512 长度的环形缓冲，128K 时滑动 KV 只有 6.29 MB，全层 KV 805.31 MB，实际驻留 0.8116 GB；8.3 表的 2.4159 GB 是共享后仍按每层全上下文分配的上界，若连共享也不做则是 5.6371 GB。

DRAM 读合计 2.3504 GB，KV 读 43,008 B，KV 写 18,432 B。时间：

- 带宽时间 2.3504 GB / 310 GB/s = 7.58 ms。
- 算力时间 2.2812 GMAC / 12.5 TMAC/s = 0.183 ms。

# 第 10 章　算子 → 硬件映射

## 10.1 分类矩阵

| 类别 | 特征 | 本模型算子 | 单 token MAC 占比（S=1） | 归属 |
|---|---|---|---:|---|
| GEMM / GEMV | 大 K、大 N、权重主导 | Q/K/V/O、MLP、PLE 投影、lm_head、塔线性 | 98.7% | 矩阵引擎 |
| 归约 | 行内求和、最大值 | RMSNorm、softmax、softcap | 0.5% | VPU |
| 逐元素 | 同形乘加、超越函数 | GELU、残差、缩放、RoPE、clip | 0.8% | VPU |
| 串行递推 | 跨 token 或跨层依赖 | 35 层链、音频轻卷积、采样循环 | 不计 MAC | 控制 / VPU |
| 查表与搬运 | 无乘加 | 主 embedding、PLE 行、KV、池化 | 0 MAC | DMA |

S=1 时 GEMM 占 98.7%，因为注意力核心只有 4,104 MAC/层。S=128K 时 GEMM 仍是 2,252,285,952 MAC，但总量涨到 9,863,388,416，占比降到 22.8%；注意力核心 7,582,195,432 占 76.9%。**同一个引擎，短上下文 98.7% 时间在跑 GEMM，长上下文 76.9% 的 MAC 在跑非 GEMM**，这是 Gemma 4 E2B 最难兼顾的一点。

## 10.2 引擎侧的三条结论

1. 短上下文利用率靠 GEMM 堆。S=1 的 GEMM 2,252,285,952 MAC 占 98.7%，其中 MLP 1,557,473,280（68.27%）、lm_head 402,653,184（17.65%）、投影 278,396,928（12.20%）、PLE 投影 13,762,560（0.60%）。只要引擎能连续跑 1536×6144 与 1536×12288 的 GEMV，短上下文利用率就能接近 99%。
2. 长上下文被注意力拖垮。S=128K 时 QKᵀ + AV 共 7.58 B MAC，是 GEMM 的 3.37 倍；矩阵引擎空闲，注意力单元成为主路径。没有独立注意力单元的芯片，128K 的实际吞吐会从 73.0 token/s 掉到 73.0 × 22.8% = 16.6 token/s 的量级。
3. 串行链的绝对时间不大，发射开销大。35 层纯计算 1,864,756,248 / 12.5 TMAC/s = 149.2 µs，占 7.58 ms 的 2.0%；但 350 次 kernel 发射 × 5 µs = 1.75 ms，占 23.1%。把每层的 Q/K/V 合并、gate/up 合并，可以把发射次数从 350 降到 150 左右，省 1.0 ms，相当于吞吐从 131.9 提到 152.0 token/s。

## 10.3 选择性与 KV 共享

| 手段 | 复用/节省倍数 | 代价 | 规划后吞吐下限 |
|---|---|---|---|
| PLE 行选读 | 2.04×（64.7 → 131.9） | 17,920 B 随机 gather，35 段 | 131.9 token/s |
| KV 共享 | 容量 2.33×（43,008 → 18,432 B） | 第 15 层等第 13/14 层，prefill 切两段 | 131.9 token/s |
| lm_head 绑定 embedding | 省 402,653,184 参数（415.13 MB） | 无 | 131.9 token/s |
| 滑动窗口 512 | 128K 少读 3.74 GB/token | 只有 512 历史可见 | 73.0 token/s |
| 双宽 MLP | 无复用 | 20 层各多 28,311,552 参数 | 131.9 token/s |

引擎吞吐下限的算法是带宽 × 算术强度：310 GB/s × 0.9705 MAC/B = 300.9 GMAC/s。这是"权重流式、KV 不爆"的下限；实际引擎的峰值算力 12.5 TMAC/s 是它的 41.5 倍，所以端侧芯片不需要大算力，需要的是 310 GB/s 持续带宽与 2.35 GB 的有效权重驻留。

KV 共享的容量收益在 128K 是 3.221 GB，但每 token 的 KV 读取字节不变：共享层仍要读共享 cache 的 K/V 做注意力。它改变的是"能开多长上下文"，不是"每 token 多快"。把 KV 共享当成带宽优化会高估收益；它真正的价值是把 128K 的常驻从 5.637 GB 压到 2.416 GB，让 8 GB 设备能跑。

## 11.2 三条硬规则

1. RMSNorm 的归约必须 FP32。1536 维在 BF16 下累加 1536 次，误差约 2⁻⁸；35 层后会把 logits 推偏 1–2%。代价是 VPU 多 1 倍寄存器，收益是省掉整模型重训。
2. 共享 KV 必须单一 dtype。第 15–34 层读第 13/14 层写的 cache；如果 base 层 BF16、共享层 FP8，要么每层转换（多 18,432 B/token 的读写），要么共享层读错。统一 FP8 可以把 128K 的 KV 从 2.416 GB 压到 1.208 GB。
3. 裁剪线性的 clamp 必须在量化前后各一次。视觉第 0 层输入上限 2.630859375、输出上限 2.5703125；把 clamp 折进量化 scale 会改变饱和点，顶层 logits 偏移。448 个视觉标量与 432 个音频标量必须逐层保留。

## 11.3 lm_head 的特殊处理

lm_head 是 262144×1536，402,653,184 MAC，415.13 MB。它占 decode 带宽 17.66%，但输出只有 262,144 个 logits，对精度极敏感。三步验证：

- 第一步，MXFP8 按 tensor scale。权重压缩到 415.13 MB，top-1 与 BF16 的一致率若低于 99.5%，进入第二步。
- 第二步，按行 scale（每个词向量一个 scale）。权重仍是 415.13 MB，一致率通常回到 99.9%；代价是 262,144 个 scale，多 0.5 MB。
- 第三步，只对 top-64 候选保留 BF16。先用量化权重算粗 logits，选出 64 个候选，再用 BF16 重算这 64 行；重算 64 × 1536 = 98,304 MAC，占 lm_head 的 0.02%，可以把 top-k 的误差压到可忽略。

若三步仍不达标，搬到 VPU：402.65 M MAC / 25 GOPS = 16.1 ms，是 7.58 ms 预算的 2.1 倍，不可行。所以 lm_head 必须留在矩阵引擎，量化误差只能靠算法侧校准，不能靠搬家解决。

## 11.4 视觉塔与音频塔的量化

| 项 | 归属 | 理由 |

最反直觉的一条是"总参数 5.86 倍，每 token 成本只有 3.03 倍"。多出的 2.83 倍（5.86 − 3.03）全部是容量项：PLE 表 2.349 B、两个塔 0.476 B、死 k/v 0.019 B。**Gemma 4 E2B 是一颗"存储按 5.28 GB、带宽按 2.35 GB、算力按 2.28 GMAC/token"设计的芯片**，三个数不能混用。

产品层结论：同一颗 310 GB/s、12.5 TMAC/s 的芯片可以同时服务两个模型。Qwen3.5-0.8B 跑 400 token/s，Gemma 4 E2B 跑 131.9 token/s；差距来自权重流量，不来自算力。SRAM 由 Gemma 的双宽 MLP 中间激活 24.6 KB 与 logits 524,288 B 决定，不由参数量决定；Qwen 的 DeltaNet 状态 18.87 MB 反而更大。若只做一颗端侧芯片，SRAM 取 1 MB 级、带宽取 310 GB/s、算力取 12.5 TMAC/s 可以覆盖两者；若要做 128K 的 Gemma，DRAM 必须 8 GB 或支持 PLE 行按需换入。
