# LiquidAI LFM3-1.7B 逐层计算拆解

2026-10-29 ｜ 依据 `LiquidAI/LFM3-1.7B` 的 `config.json`、权重清单（286 个张量，3,457,635,448 B）、`modeling_lfm3.py` / `lfm3_conv.py` / `configuration_lfm3.py` 核对

## 摘要

LFM3-1.7B 是纯文本模型，总参数 1,728,801,536（1.73 B）。24 层按三种算子混排：13 层双门控短卷积（kernel 7）、5 层滑窗注意力（窗口 256）、6 层全局注意力。hidden 2048，词表 128,000，embedding 与 lm_head 共享。

对芯片设计影响最大的几项：

- decode 每 token 读 **1.782 GB** 权重（MXFP8）。310 GB/s 下理论上限 174 token/s，按 60–70% 效率是 104–122 token/s。同为混合架构的 Qwen3.5-0.8B 是 0.776 GB / 400 token/s。
- 每 token **1,729.5 MMAC**（3.459 GFLOP），算术强度 0.970 MAC/B，与 Qwen3.5-0.8B 的 0.99 几乎相同。引擎吞吐下限因此是 301 GMAC/s。
- 跨 token 状态只剩卷积窗口：13 层 × 24.6 KB = **0.32 MB**，是 Qwen3.5-0.8B 的 18.87 MB DeltaNet 状态的 1/59。SRAM 下限第一次真正降下来，这是"卷积替代注意力"唯一的大额收益。
- 算力上没有收益。单个卷积层 64.01 MMAC，比 attention 层的 57.74 MMAC 还高 10.9%：卷积层的 mixer 是 `in_proj`（2048→6144）加 `out_proj`，比注意力的 q/k/v/o 四个投影加起来更宽。层内 73.7% 的算力在 MLP，换 mixer 只换掉 1/4。
- KV 只在 11 层产生，每 token 22.0 KB。S=256K 时实际 3.22 GB，若 24 层全是注意力要 12.88 GB，省 **9.66 GB**。KV 追上权重流量的拐点在 145K 上下文（Qwen3.5-0.8B 是 63K）。
- 最大单算子是 MLP 的 `w1`/`w3` 并联：31.46 MMAC/层，24 层 1,132.6 MMAC，占 65.5%。lm_head 262.1 MMAC 占 15.2% MAC 与 **15.2% 带宽**，比 Qwen3.5-0.8B 的 33.8% 温和得多。
- 没有 MTP 头。投机解码只能外挂草稿模型，γ=3、α=0.7、0.3 B 草稿时净加速 1.66×，低于 Qwen3.5-0.8B 自带 MTP 的 2.27×。但回滚极便宜：状态快照只要 0.32 MB 加 KV。
- 精度的新风险不在 attention 而在卷积：conv 的输入是两个投影的逐通道乘积 `B ⊙ x`，重尾分布，MXFP8 的 32 元素块缩放对它系统性偏差；卷积权重每通道只有 7 个抽头，块内混进时间维。

后面按"模型事实、层结构、逐算子、算力与带宽、硬件映射、量化、结论"展开。

# 第 1 章　事实基线

## 1.1 数据来源与核对方法

本篇按 `LiquidAI/LFM3-1.7B` 分析。这个 repo 存在，`config.json` 的 `architectures` 是 `Lfm3ForCausalLM`，`model_type` 是 `lfm3`，README 自称 tri-hybrid，与请求的 LFM3-1.7B 型号一致，不存在退回其它型号的问题。同名的 `LiquidAI/LFM3-1.7B-Instruct` 返回 404，`LFM3-1.7B` 本身就是 instruct 主线（README 写的是 post-trained for agentic harnesses），但建模代码的 docstring 里还残留 `LiquidAI/LFM3-1.7B-Preview` 的旧名，说明这个 repo 改过名。家族里另有 `-Base`、`-FP8`、`-NVFP4`、`-GGUF`、`-ONNX`、`-MLX-4bit` 等衍生仓库，参数与架构相同，只换精度与权重格式。

材料有四类：`config.json`（1,454 B，24 条 `layer_types` 全部实读，不凭印象）；单文件权重 `model.safetensors` 的 header（32,368 B，286 个张量，全部 BF16）；`modeling_lfm3.py` 与 `lfm3_conv.py`（决定了算子顺序、卷积的 kernel 与状态长度、部分 RoPE 的两套参数）；`configuration_lfm3.py`（决定了 `layer_types` 的默认生成规则）。没有读到训练侧 kernel，也没有官方论文，所以"训练时卷积怎么实现"这一项未核到，记在 12.3。

核对方式有两条。

第一，header 元素数之和 1,728,801,536，权重文件 3,457,635,448 B 减去 8 B 长度前缀与 32,368 B header 后除以 2（全 BF16），得 1,728,801,536，**差额 0 个参数、0 B**。这和 Qwen3.5-0.8B 的 2,592 差额不同：那边是分片文件与张量边界的对齐填充，这里是单文件，所有张量端点恰好落在 8 B 边界上，没有填充。

第二，逐层求和：13 × 63,985,664 + 11 × 57,712,896 + 262,144,000 + 2,048 = 1,728,801,536，与 header 分组统计逐位相符。张量个数也对得上：13 × 10 + 11 × 14 + 2 = 286，与 header 的元素数完全一致，说明没有漏掉任何一层、任何一个小张量。

一个命名坑先说清楚：config 里的 `conv_L_cache: 7` 名字像"缓存长度"，代码里却是 `self.conv_kernel_size = config.conv_L_cache`，即卷积核宽度为 7，缓存长度是 kernel−1 = 6。按名字理解会把状态大小算大 16.7%。

## 1.2 关键超参

| 项 | 值 | 与 Qwen3.5-0.8B 的差异 |
|---|---|---|

| `num_attention_heads` × `head_dim` | 16 × 128 | 0.8B 是 8 × 256，总宽都是 2048 |
| `num_key_value_heads` | 4（GQA 4:1） | 0.8B 是 2（GQA 4:1） |
| `sliding_window` | 256 | 0.8B 无此参数 |

| `tie_word_embeddings` | true | 相同 |
| `norm_eps` | 1e-5 | 0.8B 是 1e-6 |
| `use_sandwich_norm` | true，每层 4 个 norm | 0.8B 每层 2 个 norm |
| `partial_rotary_factor` | 0.5 只给全注意力层（128 维里转 64 维）；滑窗层缺省 1.0（全转） | 0.8B 是 0.25（256 里转 64） |
| `rope_theta` | 1e6（全注意力）/ 1e4（滑窗） | 0.8B 是 1e7 |
| `max_position_embeddings` | 262144 | 相同 |
| 输出门控 | 每头 1 个标量，共 16 维 | 0.8B 是每通道 1 个，共 2048 维 |
| MTP | 无 | 0.8B 有 1 层 MTP |
| 视觉塔 | 无（本 checkpoint） | 0.8B 有 12 个 block、100.59 M |
| `conv_bias` / 所有 `bias` | false | 0.8B 部分投影带 bias |
| 权重 dtype | BF16 | 相同 |

三处值得单独说。

**sandwich norm 把归一化次数翻了一倍。** 每层有 `operator_norm`、`post_operator_norm`、`ffn_norm`、`post_ffn_norm` 四个，mixer 与 MLP 的输出都要先归一化再进残差。MAC 上只多 0.49 M（占 0.03%），但它是精度设计的关键：分支输出在入残差前被重新归一，尺度有界，这对量化的帮助比对算力的影响大得多。Qwen3.5-0.8B 只有两个。

**head 几何从 8×256 换成 16×128。** 总宽都是 2048，但 q_norm/k_norm 是按 head_dim 做的：0.8B 每头 256 维、8 条归约，LFM3 每头 128 维、16 条归约。归约条数翻倍、每条减半，并行度要求更高，单条加法树的级数少一级。

**词表只有 128K，是 0.8B 的一半。** 这一项直接决定了 lm_head 的带宽占比从 33.8% 降到 15.2%，是 LFM3 在 decode 上比 0.8B 更"干净"的主要原因。

# 第 2 章　模型全景

## 2.1 两个子模型

```
LFM3-1.7B ─┬─ 文本主干   1,466,655,488 ─┬─ 13 × 卷积层       831.8 M
            │                            ├─ 6 × 全注意力层    346.5 M
            │                            ├─ 5 × 滑窗注意力层  288.7 M
            │                            └─ final norm         2.0 K
            └─ 输出头      262,144,000 ──  embed / lm_head 共享
```

只有一个可执行子模型：文本主干加共享输出头，两者都参与 decode 与 prefill。没有视觉塔，没有 MTP，没有投影适配器。纯文本推理需要的权重就是全部 1.73 B，MXFP8 下 1.782 GB——这个数比 Qwen3.5-0.8B 的整个模型加 KV 还大，因为那边的 100.59 M 视觉塔和 20.45 M MTP 在这边换成了 24 层全宽 MLP。

家族里另有 vision/audio/omni 成员，本 repo 里没有它们的权重，结构未核到。第 7 章只算输出头。

## 2.2 文本主干的层型配比

`layer_types` 从 config 实读：第 0、1 层 conv，第 2 层全注意力，第 3 层 conv，第 4 层滑窗，之后每 4 层重复一次"full → conv → sliding → conv"。等价于"索引 i % 4 == 2 是全局注意力，i % 4 == 0 且 i > 0 是滑窗，其余是卷积"。

| 层型 | 层数 | 每层参数 | 每层 MAC（decode） | 结构特征 |
|---|---:|---:|---:|---|
| A　双门控短卷积 | 13 | 63.99 M | 64.01 M | in_proj 三倍宽 + 逐通道门控 + depthwise k=7 |
| B　全注意力 | 6 | 57.71 M | 57.74 M | GQA 4:1 + 部分 RoPE + 每头标量门 |
| B'　滑窗注意力 | 5 | 57.71 M | 57.74 M | 同上，窗口 256，RoPE 全维 |
| M　SwiGLU MLP | 24（每层一份） | 47.19 M | 47.19 M | w1/w3 双投影 + SiLU + w2 |

13 : 5 : 6 的比例让全局注意力每 4 层出现一次，滑窗层插在中间，卷积填满剩余。这么排的原因可以从数字上推：全注意力层的 S 相关项是每 token 4,112·S MAC，S=32K 时 134.7 MMAC/层，是固定部分的 2.3 倍；把它的层数压到 6 层，S 项总量才 808.5 MMAC，仍不到固定总量 1,729.5 MMAC 的一半。若 24 层全用注意力，S=32K 时仅 QKᵀ/AV 就是 3.23 GMAC，decode 的算力账直接翻三倍。

Qwen3.5-0.8B 用 18 层 DeltaNet + 6 层注意力达到同样的 3:1 效果，LFM3 用 13 层卷积 + 5 层滑窗 + 6 层注意力。两者的共同点是"全局注意力层数都是 6"，差别在剩下的 18 层怎么填：一个是带 128×128 递推状态的线性注意力，一个是 6 个 token 窗口的深度卷积。

## 2.3 计算形态的六个类别

| 类别 | 特征 | 本模型里的算子 | 典型维度 |
|---|---|---|---|
| 稠密矩阵乘（GEMM / GEMV） | 激活 × 权重 | 全部 `*_proj`、`lm_head`、QKᵀ、A·V | K 是读入维，N 是输出维 |
| 归约 | 沿一维求和或求最值 | 97 次 RMSNorm、softmax | 2048 / 128 / S |
| 逐元素 | 同形状逐点 | 门控乘、SiLU、sigmoid、残差、RoPE | 2048 / 7680 / 16 |
| 串行递推 | 后一步依赖前一步 | 卷积窗口滚动（6 个 token） | 2048 通道 × 6 |
| 查表 | 索引取行 | `embed_tokens` | 128,000 行 |
| 搬运 | 无计算 | KV cache 追加、卷积状态写回、量化 pass | 2 KB/token/层 |

和 Qwen3.5-0.8B 比，第四类从"矩阵状态的 delta 递推"降级成"滚动窗口"。这不是量级差别，是性质差别：delta 递推每 token 要读改写 1 MiB 的 FP32 状态、5 拍硬串行；卷积窗口只读改写 24.6 KB 的 FP16 历史，3 拍串行（门控 → 卷积 → 门控）。

## 3.2 层的通用骨架

两种层共用同一个模板，差别只在 mixer。注意这里的骨架比 Qwen3.5-0.8B 多两次归一化。

```
x [1,2048]
 │
 ├─► [G0] operator_norm ─► r [1,2048]
 │                           │
 │                           ▼
 │                     y = mixer(r)  [1,2048]      ← 3.3 卷积 / 3.4 注意力
 │                           │
 │                           ▼
 │                   post_operator_norm ─► y' [1,2048]
 │                           ▼
 └─► x = x + y' ◄────────────┘                     ← 残差①
 │
 ├─► ffn_norm ─► r2 [1,2048]
 │                  │
 │                  ▼
 │            z = mlp(r2)  [1,2048]                ← 3.5
 │                  ▼
 │            post_ffn_norm ─► z' [1,2048]
 │                  ▼
 └─► x = x + z' ◄───┘                              ← 残差②
 │
输出 x [1,2048]（形状与输入完全相同）
```

**读图约定（第 3 章所有 DAG 通用）**

| 记号 | 含义 |
|---|---|
| `─►` | 同 token 内的数据依赖，箭头上带计算 |
| `┄` | 纯视图（chunk / reshape / transpose），0 MAC，只改索引与 stride |
| `═` | 跨 token 状态读写（卷积窗口 / KV cache） |
| `[G0]` `[G1]` … | 并行组：同组内互不依赖，可并发发射；组号小的必须先完成 |
| 横向分支 | 只表示并行关系，不表示时间先后；汇合点之前的所有分支都必须就绪 |

层内只有三种形状变换：

| 变换 | 形状关系 | 例子 | 通道语义 |
|---|---|---|---|
| 稠密线性 | `[K] → [N]` | `in_proj` 2048→6144、`w1` 2048→7680 | 全部通道混合 |
| 逐元素 / 逐通道 | `[N] → [N]` | 门控乘、RMSNorm 缩放、SiLU、残差 | 一进一出，通道对齐 |
| 纯视图 | `[N] → [M₁]…[Mₖ]` | `chunk(3)` 6144→3×2048、`view(…,16,128)` | 不改数，只改索引 |

残差流宽度恒为 `[2048]`，24 层不变。这个宽度决定了两件事：每次残差读写 4 KB（FP16），以及每次 RMSNorm 是一条 2048 宽的归约。Qwen3.5-0.8B 的残差流是 1024，同样的操作量减半；但 LFM3 每层 4 次归一，0.8B 每层 2 次，一加一减之后两边的归一化总量差不了多少。

## 3.3 层型 A：双门控短卷积（13 层）

卷积层替代注意力的方式很直接：不做任何跨 token 的加权求和，只把最近 7 个 token（含自己）的同一个通道做一次加权和，权重逐通道独立学。信息压缩比是 7:1，没有 KV，没有增长的状态。

子模块全部挂在 `layers.N.conv.*` 下：

| 张量 | 形状 | 作用 |
|---|---|---|
| `conv.in_proj` | [6144, 2048] | 一次投影出 B、C、x 三段，各 2048 |
| `conv.conv` | [2048, 1, 7] | depthwise，groups = 2048，kernel 7，dilation 1 |
| `conv.out_proj` | [2048, 2048] | 输出投影 |
| `operator_norm` / `post_operator_norm` | [2048] | 骨架自带 |
| `ffn_norm` / `post_ffn_norm` | [2048] | 骨架自带 |

数据流是"门控 → 卷积 → 门控"：

```
BCx = in_proj(r)          ┄ chunk(3) → B, C, x   各 [1,2048]
u   = B ⊙ x                                      ← 第一道门，逐通道
v   = conv_k7(u)  ═ 窗口 [2048, 6]                ← 深度卷积，跨 token
y   = C ⊙ v                                      ← 第二道门，逐通道
out = out_proj(y)
```

两个必须记住的点。**门控在卷积之前**：进窗口缓存的是 `B ⊙ x`，不是 `x`，也不是 `r`。硬件重排流水时必须把状态写回点放在门控乘之后，否则缓存里存的是另一个量，形状对得上、数值全错。**卷积分支里没有任何非线性**：整个 mixer 只有两次逐通道乘和一次深度卷积，SiLU 只出现在 MLP 里。这一点与 LFM2 一致，也是它与 Qwen3.5-0.8B 的 DeltaNet 分支最大的差别（后者在卷积后接 SiLU）。

### 3.3.3 关键路径与并行机会

- 关键路径：`G0 → G1 → G2 → G3 → G4 → G5 → G6 → G7 → G8 → G9(w1) → G10 → G11 → G12 → G13 → G14`，共 15 段，其中 4 段是矩阵乘。
- `C` 支路从 G1 产出、G4 消费，中间跨一次卷积，是层内生命周期最长的一份数据（4 KB）。硬件上它必须驻留寄存器或 SRAM，否则 G4 要回头再读一次 4 KB。
- 卷积只有 14,336 MAC（占本层 0.02%），但它是唯一的跨 token 段，也是唯一的"读改写"段：24.6 KB 窗口读进来、左移一格、写回去。
- 单层 64.01 MMAC 里，两个投影 16.78 M（26.2%）、MLP 47.19 M（73.7%）、卷积与门控 18,432（0.03%）、归一与残差 12,288（0.02%）。**卷积本身在算力上可以忽略，它的成本全在状态管理和流水串行上。**
- 与 Qwen3.5-0.8B 的 DeltaNet 层对比：那边 mixer 8.42 M 投影 + 0.83 M 递推 = 9.25 M，这边 16.78 M；那边每层状态 1.05 MB，这边 24.6 KB。算力涨 81%，状态降到 1/43。

## 3.4 层型 B：注意力（11 层，全 + 滑窗）

注意力层是标准 Llama 结构加四个改动：QK 各自做 per-head RMSNorm、每头一个 sigmoid 标量门、部分 RoPE、滑窗层加 256 窗口。

| 张量 | 形状 | 作用 |
|---|---|---|
| `q_proj` | [2048, 2048] | 16 头 × 128，正好等于 hidden |
| `k_proj` / `v_proj` | [512, 2048] | 4 个 KV 头 × 128 |
| `o_proj` | [2048, 2048] | 输出投影，在门控之后 |
| `q_norm` / `k_norm` | [128] | 按 head_dim 归一，16 条与 4 条 |
| `gate_proj` | [16, 2048] | 每头 1 个标量门 |

与全注意力层的唯一结构差别是 `sliding_window = 256` 与 RoPE 参数（theta 1e4、全维旋转）。这两项都不改形状，只改 mask 与角度表。

### 3.4.3 关键路径与并行机会

- 关键路径：`G0 → q_proj → q_norm → RoPE → Q·Kᵀ → softmax → A·V → 门控 → o_proj → 残差`。K/V 两条支路不延长路径，但它们的写缓存在 G4/G6 之前必须完成。
- 门控是层内跨度最大的旁路：G1 产出、G7 消费，中间隔三次矩阵乘加一次 softmax。它只有 16 个标量，32 B，但必须活到最后。
- 顺序不可重排的三处：`q_norm` 在 `view(16,128)` 之后（按 128 维归一，不是按 2048）、RoPE 在写 cache 之前、门控在 `o_proj` 之前。
- 滑窗层的 `Q·Kᵀ` 与 `A·V` 实际长度是 `min(S, 256)`，不是 S。硬件若按 S 分配 KV 缓冲，S=4K 时 5 层滑窗要多占 39.3 MB（每层 7.86 MB），是真实需求的 16 倍。
- S=4096 时 QKᵀ+AV 是 16.78 MMAC/层，已经是四个投影 10.49 MMAC 的 1.6 倍；S=32K 时是 12.8 倍。全局注意力的成本重心在 S，不在权重——这与 Qwen3.5-0.8B 的结论相同，但它那边是 8 头 × 256，这边是 16 头 × 128，QKᵀ 的乘加次数完全一样（2048·S）。

## 3.5 子模块 M：SwiGLU MLP（24 层各挂一份）

| 张量 | 形状 | 作用 |
|---|---|---|
| `feed_forward.w1` | [7680, 2048] | 门控分支 |
| `feed_forward.w3` | [7680, 2048] | 值分支 |
| `feed_forward.w2` | [2048, 7680] | 回投 |

计算 `y = w2( silu(w1(x)) ⊙ w3(x) )`。`w1` 与 `w3` 共用同一个 2048 维输入，可以合成一次 `1×2048×15360` 发射、输出分两段写，是层内唯一可并行的两支（DAG 见 3.3.1 的 G9–G12）。24 层完全同构，是模型里最规整的部分。

单层 47.19 MMAC 里 w1+w3 占 31.46 M（66.7%）、w2 占 15.73 M（33.3%），SiLU 与门控乘共 7,680；24 层合计 1,132.84 MMAC，占总 MAC 的 65.5%。tile 只有一种合理选择：N 按 512 切 15 份（w1/w3）或 4 份（w2）；K=7680 是全模型最长的 K 维，整块进。

`intermediate_size / hidden = 3.75`，比 Qwen3.5-0.8B 的 3.5 略宽。Qwen 的 MLP 是 264.35 MMAC、占 34.5%，这边 1,132.84 MMAC、占 65.5%——差近一倍的原因不是 MLP 特别大（3.75 倍宽对 3.5 倍宽），而是 lm_head 小了一半（128K 对 248K 词表）。

## 3.6 输出头

| 张量 | 形状 | 作用 |
|---|---|---|
| `embed_tokens` | [128000, 2048] | 查表，同时充当 lm_head |
| `embedding_norm` | [2048] | 主干末端归一 |

没有 MTP。投机解码若要用，只能外挂一个独立草稿模型，代价见 10.3。Qwen3.5-0.8B 在这里多一个 20.45 M 的 MTP 头，这是两者在 decode 加速手段上的结构性差别。

## 3.7 层间差异速查

13 层卷积完全同构，张量名、形状、算子顺序一致。11 层注意力也只有两处差别：5 层滑窗的 `Q·Kᵀ`/`A·V` 长度是 256、RoPE 全维（theta 1e4）；6 层全局的窗口是全长、RoPE 只转前 64 维（theta 1e6）。两者参数量完全相同，都是 57,712,896，差别只在 mask 与角度表；24 个 MLP 也完全一样。位置信息只从 RoPE 进来，卷积层靠 7 抽头窗口隐式携带局部次序。

## 3.8 单层内部张量流（以 layer 0 为例）

逐行追踪 layer 0（卷积层）在 decode 时的形状变化，`[G]` 编号与 3.3.1 对应。

```
x                        [1, 2048]          ← 残差流，FP16
│
├ [G0] operator_norm ► r  [1, 2048]                       归约 2048
│
├ [G1] in_proj ─────────► BCx [1, 6144]                   GEMM 2048×6144 → 12.97 MB
│      └ ┄ chunk(3) ────► B, C, x 各 [1, 2048]            0 MAC
│
├ [G2] u = B ⊙ x ───────► u [1, 2048]                     逐通道
│
├ [G3] conv(k=7) ───────► v [1, 2048]                     14,336 MAC
│      └ ═ 窗口 [2048, 6]  读 24.6 KB、写 24.6 KB         跨 token
│
├ [G4] y = C ⊙ v ───────► y [1, 2048]                     逐通道

├ [G6] post_operator_norm ► m' [1, 2048]                  归约 2048
│
x = x + m'  [G7]          [1, 2048]                      逐元素
│
├ [G8] ffn_norm ────────► r2 [1, 2048]                    归约 2048

├ [G12] w2 ─────────────► z [1, 2048]                     GEMM 7680×2048 → 16.22 MB
```

对硬件和测试最直接的三点：

2. 切分点就在 `[G]` 边界。G1 的输出 6144 维要在 DMA 落盘时就按 2048/2048/2048 分段存，否则 G2 与 G4 都要回头再读。
3. 只有 G3 跨 token。窗口 24.6 KB 是这一层唯一的跨 token 依赖，也是整个模型唯一需要"左移一格"的写操作。

# 第 5 章　通用算子库

全模型只用到 5 个通用算子：RMSNorm、逐通道门控乘、SiLU、因果深度卷积、部分 RoPE。后面任何一层都是这几个的排列组合。

它们都上不了矩阵引擎，原因各不相同：RMSNorm 是行内归约，门控乘是逐通道（K=1），SiLU 是超越函数，卷积是跨 token 滑窗，RoPE 是跨 lane 置换。

decode 一个 token 的调用次数：RMSNorm 97 次（24 层 × 4 + final 1），门控乘 37 次（13 层 × 2 加 11 层 × 1），SiLU 24 次，深度卷积 13 次，RoPE 11 次。

## 5.1 RMSNorm

**作用**：按行归一化，再乘一个可学习的逐通道增益。
**公式**：

```
y_i = x_i · rsqrt(mean(x²) + 1e-5) · w_i
```

与 Qwen3.5 系的 `1 + w` 不同，这里是标准的 `w`，初始化就是 1。移植时若沿用 Qwen 的 `1+w` 打包，权重会被整体加 1，输出幅度直接翻倍——这是一个只改一行、结果全错的错误。

**形状**：`[1,2048] → [1,2048]`，归约维 2048；`q_norm`/`k_norm` 是 16 条与 4 条 128 维归约。
**MAC**：主体 2 × 2048 = 4,096，97 次合计 397,312（0.02%）。q/k norm 11 层 × 5,120 = 56,320。
**精度**：平方和 FP32 累加，输入先升 FP32，缩放后降回 FP16。2048 个 FP16 平方直接相加会丢约 3 位。
**坑**：
1. 增益是 `w` 不是 `1+w`。这是与 Qwen 系最容易混的一处。
2. 每层 4 个 norm，是 Qwen3.5-0.8B 的两倍。流水线入口的固定开销从 2 次归约变成 4 次，decode 时无所谓，prefill 时这 4 条 2048 宽归约要能在同一拍发射。
3. `post_operator_norm` 与 `post_ffn_norm` 的输入是投影输出（FP32 累加结果），若在归一前就截成 FP16，会损失 1 位以上；归一后的值再降位才对。

## 5.2 逐通道门控乘

**作用**：卷积层的两道门。第一道门控住进窗口的信号，第二道门控住卷积的输出。
**公式**：

```
u_c = B_c · x_c          (第一道，在卷积之前)
y_c = C_c · v_c          (第二道，在卷积之后)
```

**形状**：`[1,2048] × [1,2048] → [1,2048]`，两组，逐通道，不做任何跨通道混合。
**MAC**：2 × 2048 = 4,096/层，13 层共 53,248。
**精度**：两个因子都是投影输出，乘积的分布是重尾的（两个近似高斯的乘积，超额峰度约 6，单变量为 0）。这是 MXFP8 在这一层最难受的地方，见 11.4。
**坑**：
1. 顺序是"门控 → 卷积 → 门控"，不是"卷积 → 门控"。第一道门藏在卷积之前，容易漏。
2. 乘积的数值范围比单个投影宽 2–3 倍，静态 scale 必须按乘积后的最大值定，按 `B` 或 `x` 的 scale 定会削顶。
3. 这道乘没有非线性，所以它不改变重尾性质，只放大动态范围。

## 5.3 SiLU

**作用**：MLP 的门控激活，`silu(x) = x·σ(x)`。
**形状**：`[1,7680]`，24 层共 184,320 次。
**MAC**：门控乘 7,680/层，24 层 184,320。SiLU 本身算一次 exp 加一次乘。
**精度**：负半轴放大误差（`silu(−8) ≈ −2.7e-3`，输入误差被 σ 的斜率放大），必须 FP16。E4M3 在负半轴相对误差可达 6%。
**坑**：
1. 用 LUT 时表按 FP16 索引，16K 项 × 16 bit = 32 KB，可常驻 SRAM。
2. 7680 维比 hidden 宽 3.75 倍，逐元素单元按 7680 设计，不要按 2048 设计。
3. 门控乘必须在 SiLU 之后、`w2` 之前。

## 5.4 因果深度卷积（卷积层专用）

**作用**：给卷积层提供唯一的跨 token 感受野。kernel 7，dilation 1，groups = 2048，左填充 6。
**公式**：

```
v_{c,t} = Σ_{j=0..6} W[c,j] · u_{c,t+j−6},   c = 1..2048
```

**形状**：`[1,2048] + 窗口 [2048,6] → [1,2048]`。窗口存的是过去 6 个 token 的 `u = B ⊙ x`。
**MAC**：2048 × 7 = 14,336/层/token，13 层共 186,368（占全模型 0.01%）。
**精度**：FP16。卷积权重只有 7 个值/通道，量化到 FP8 时块内会混进 7 个时间抽头，见 11.4。
**坑**：
1. 窗口长度是 **6**，不是 7。kernel = 7 时需要 6 个历史加当前 1 个，多加一格不会报错，只会让第一格永远算 0。
2. 写回是"左移一格 + 写新值"的读改写，24.6 KB。只写新值不左移，单 token 测试看不出来，第 3 个 token 之后才开始错。
3. 窗口的输入是门控之后的值。硬件若在 `in_proj` 之后就存窗口，存的是 6144 维的未门控量，状态大 3 倍、语义也不对。
4. 文档边界要清零窗口：代码用 `last_document` 掩码把跨文档的历史置 0。连续 decode 时窗口天然只含本文档，但 packed prefill 必须处理，漏了会让两个文档串味。
5. 与 Qwen3.5-0.8B 的短卷积比较：那边是 k=4、作用在 6144 维 qkv 上、后面接 SiLU，24,576 MAC；这边是 k=7、作用在 2048 维门控信号上、无 SiLU，14,336 MAC。**LFM3 的卷积更宽但更窄，MAC 反而少 42%**。

## 5.5 部分 RoPE（注意力层专用）

**作用**：给 Q/K 注入位置信息。两种参数：

```
全注意力层：theta = 1e6，partial = 0.5 → 32 个角度，旋转前 64 维，后 64 维透传
滑窗层：    theta = 1e4，partial = 1.0 → 64 个角度，旋转全部 128 维
```

**公式**（half-split，以全注意力层为例）：

```
θ_i = pos / 1e6^(i/32),  i = 0..31
q'_i      = q_i      · cos θ_i − q_{i+32} · sin θ_i
q'_{i+32} = q_{i+32} · cos θ_i + q_i      · sin θ_i
q'_j = q_j,   j = 64..127（透传）
```

**形状**：`q [1,16,S,128]`、`k [1,4,S,128]`；`cos/sin [S,64]`（全层）或 `[S,128]`（滑窗层）。
**MAC**：每对 4 次乘加。全层 q 16 × 32 × 4 = 2,048，k 4 × 32 × 4 = 512，合计 2,560/层；滑窗层 q 16 × 64 × 4 = 4,096，k 4 × 64 × 4 = 1,024，合计 5,120/层。
**精度**：角度必须在 FP32 里算（代码是 `position_ids.float() * inv_freq`）。262144 已经超过 FP16 的最大有限值 65,504，位置在里面直接溢出为 inf；即便只看 32,768，FP16 的整数 ulp 也是 32，乘上 inv_freq 之后角度误差仍可达数十弧度，旋转完全失效。
**坑**：
1. 两套角度表，不能共用。全层 32 个非零频率 + 32 个零，滑窗层 64 个非零。硬件若按层型切换参数，切换点在第 2/4/6/8… 层，共 11 处。
2. half-split 不是 interleaved。劈成前后两半再配对，按 interleaved 实现形状对、数值错。
3. cos/sin 表不要按 S 预存：128 维 × 262144 位置 × 2 B = 67 MB。现算每 token 只有 32 或 64 对三角函数。
4. 与 Qwen3.5-0.8B 比：那边是 8 头 × 256 维里转 64 维（2,560 MAC），这边全层是 16 头 × 128 维里转 64 维（2,560 MAC）——总 MAC 一样，但角度表宽度不同，不能直接搬。

# 第 6 章　两种层型的逐算子拆解

这一章把两种层型拆成算子卡：卷积层 A①–A⑭，注意力层 B①–B⑲。每张卡的字段固定：形状、MAC、归属、精度、坑。MAC 统计包含逐元素与归约，只排除纯视图——这样每张表都能直接相加，与第 8 章的总账对上。

两个前提先摆出来。卷积层单层 64.01 MMAC，比注意力层 57.74 MMAC 高 10.9%，所以"层数多"不等于"算力多"，卷积层只占 48.1% 的 MAC。真正的算力在 MLP：24 层合计 1,132.6 MMAC，占 65.5%。

## 6.1 层型 A：双门控短卷积（13 层）

### A① 前置 RMSNorm

| 项 | 内容 |
|---|---|
| 形状 | `[1,2048] → [1,2048]` |
| MAC | 4,096 |
| 归属 | VPU（2048 宽归约） |
| 精度 | 平方和 FP32，输出 FP16 |
| 坑 | 增益是 `w` 不是 `1+w`；每层 4 个 norm 是流水线固定开销 |

### A② in_proj（2048→6144）

| 项 | 内容 |
|---|---|
| 形状 | `[1,2048] → [1,6144]`，输出按 2048 三段切 |
| MAC | 12,582,912（占本层 19.7%） |
| 归属 | 矩阵引擎，MXFP8 |
| 精度 | 权重 MXFP8，激活 MXFP8，输出 FP32 |
| 坑 | 三段语义不同：B 与 x 进乘法、C 留到最后；DMA 落盘必须分段 |

这是卷积层最大的一笔 MAC，也是它与注意力层最不像的地方：注意力是三条独立投影（2048/512/512），卷积是一条三倍宽的融合投影。算术强度 12,582,912 MAC ÷ 12.97 MB = 0.970 MAC/B，与全局平均相同。

### A③ 门控乘 ①（B ⊙ x）

| 项 | 内容 |
|---|---|
| 形状 | `[1,2048] × [1,2048] → [1,2048]` |
| MAC | 2,048 |
| 归属 | VPU，逐通道 |
| 精度 | FP16 计算，结果即窗口输入 |
| 坑 | 乘积重尾，动态范围比单个投影宽 2–3 倍；这一步的量化误差会进窗口并停留 7 个 token |

### A④ 因果深度卷积（kernel 7）

| 项 | 内容 |
|---|---|
| 形状 | `[1,2048] + 窗口 [2048,6] → [1,2048]` |
| MAC | 14,336（2048 × 7） |
| 归属 | VPU + 状态缓存，不能上引擎 |
| 精度 | FP16；权重 7 值/通道 |
| 坑 | 跨 token；kernel 7 需要 6 个历史；读改写 24.6 KB；文档边界清零 |

kernel = 7、dilation = 1、padding = 6（左）、groups = 2048。卷积核在时间轴上的跨度是 7，感觉野是 7 个 token——这就是整个模型对"局部上下文"的全部建模。它不随上下文增长，也不随 hidden 变化，只随层数线性增长。

### A⑤ 门控乘 ②（C ⊙ v）

| 项 | 内容 |

| 形状 | `[1,2048] × [1,2048] → [1,2048]` |
| MAC | 2,048 |
| 归属 | VPU |
| 精度 | FP16 |
| 坑 | C 从 A② 产出到这里才用，跨一整次卷积，是层内寿命最长的 4 KB |

### A⑥ out_proj（2048→2048）

| 项 | 内容 |
|---|---|
| 形状 | `[1,2048] → [1,2048]` |
| MAC | 4,194,304（6.6%） |
| 归属 | 矩阵引擎，MXFP8 |
| 精度 | 输出 FP32，直通后置归一 |
| 坑 | 方阵，tile 划分无歧义；K 维 2048 与注意力层相同 |

### A⑦ 后置归一

| 项 | 内容 |

| MAC | 4,096 |
| 归属 | VPU |
| 精度 | 输入是 FP32 累加结果，先升 FP32 归一 |
| 坑 | 这是 sandwich norm 的后半，漏掉它不会报错，只是残差幅度失控 |

### A⑨–A⑭ MLP 与后置归一

MLP 的六个算子（`ffn_norm` 4,096、`w1`+`w3` 31,457,280、SiLU、门控乘 7,680、`w2` 15,728,640、`post_ffn_norm` 4,096、残差 2,048）就是全部，与注意力层完全一致，合计 47,201,792，结构与 tile 见 3.5。

| 项 | MAC | 占比 |

### A⑯ 硬件归属：哪些能上 MXFP8 矩阵引擎

| 算子 | 能否上引擎 | 原因 |
|---|---|---|
| A② `in_proj` | 最佳目标 | 纯 GEMM `1×2048×6144`，K=2048 |
| A⑥ `out_proj` | 最佳目标 | `1×2048×2048` |
| A③⑤ 门控乘 | 不能 | K=1，逐通道，引擎的 K 维退化 |
| A④ 深度卷积 | 不能 | 跨 token 滑窗 + 逐通道，累加器结构不匹配 |
| A①⑦ norm | 不能 | 行内归约 |
| MLP `w1`/`w3`/`w2` | 最佳目标 | 见 3.5 |

| MLP `w2` | MXFP8 | MXFP8 | FP32 | **FP32** |

### A⑱ 实现/测试坑（按优先级）

1. **窗口写回点放错**。窗口必须存 `B ⊙ x`。若在 `in_proj` 后直接存 6144 维，状态大 3 倍且数值语义错，单 token 测试完全正常。
2. **窗口左移漏掉**。只写新值不左移，前 2 个 token 正确，第 3 个开始漂移。测试必须跑连续 8 个 token 并对拍。
3. **conv 输入量化到 MXFP8**。重尾乘积进 32 元素块缩放，误差会经 7 个 token 的窗口累积。先用 FP16 打通，再单独评估。
4. **kernel 数与窗口长混淆**。`conv_L_cache=7` 是 kernel，窗口是 6。按 7 分配状态会多 16.7%，且第一格恒为 0。
5. **门控乘当成逐元素 K=2048 的 GEMM**。它没有 K 维归约，送上引擎等于发射一次 N=2048、K=1 的退化 GEMV，利用率 1/2048。
6. **三段输出的落盘顺序**。B、C、x 三段的读取时刻不同（B 与 x 最早，C 最晚），若混排存放，C 的 4 KB 会被提前换出。

### 6.2.5 十个必须记住的坑（按危害排序）

1. **滑窗层按全长分配 KV**。5 层滑窗层的 cache 恒为 2.62 MB，按 S 分配在 S=256K 时多占 2.68 GB，是权重流量的 1.5 倍。
2. **`repeat_kv` 按 16 头各读一份**。KV 带宽变 4 倍：S=32K 时从 402.7 MB 涨到 1.61 GB。
3. **两套 RoPE 参数混用**。全层转 64 维、滑窗层转 128 维，混用后滑窗层的位置信息少一半，短上下文几乎看不出来，长上下文崩。
4. **softmax 用 FP16**。S=32K 时行最大值与指数和都在 FP16 边界上。
5. **p 量化到 FP8**。p ∈ [0, 0.05] 且长尾，E4M3 相对误差 6%。
6. **门控当逐通道用**。它是每头一个标量，广播到 128 维；按逐通道实现（2048 个值）会读出越界的权重。
7. **q_norm 在 view 之前**。按 2048 维归一会得到完全不同的数值，形状仍然对。
8. **scaling 放在 softmax 之后**。0.0884 必须在 exp 之前乘。
9. **滑窗 mask 用全局 mask**。窗口外的项必须置 −inf，否则等价于全局注意力，S=32K 时多算 128 倍。
10. **KV 精度混用**。K 与 V 一个 FP16 一个 FP8，p 的分布会偏斜。

本节的三张表分别进第 8 章：57,742,352 进 8.1 算力账，三档 KV 进 8.3 缓存账，59.50 MB 进 8.2 带宽账；B⑧ 的 softmax 与 A④ 的卷积窗口就是 10.2 说的"两处串行"。

## 6.3 输出头（E1–E4）

**E1 final norm**：`[1,2048]`，4,096 MAC，VPU。名字是 `embedding_norm`，不叫 `norm`，DMA 按名查表时容易漏。

**E2 lm_head（= `embed_tokens`）**：`[1,2048] → [1,128000]`，262,144,000 MAC（15.2%），矩阵引擎 MXFP8（待验证），输出 FP32 logits。与 embedding 共享权重，量化策略必须同时满足查表与输出两个用途。

**E3 embedding 查表**：0 MAC，读 4 KB（一行 2048 × 2 B）。prefill 时是 M=S 的 gather，decode 时是一次 4 KB 突发的随机读。

**E4 logits 缓冲**：128,000 × 4 B = 512 KB。整块留 SRAM 占 0.5 MB；分块算则采样要扫两遍。采样本身见 7.3：全排序 2.18 M 次比较，占预算 42–77%。

# 第 7 章　输出头与采样（无视觉塔）

## 7.1 视觉塔：本 checkpoint 没有

`LiquidAI/LFM3-1.7B` 的 header 里没有任何视觉张量，`config.json` 里没有 `vision_config`，`modeling_lfm3.py` 只有文本路径。家族里的 vision/audio/omni 成员是独立仓库，结构与参数量未核到。

这对本篇的影响是：第 7 章没有 V①–V⑩ 可拆，7.2–7.4 改为输出头的逐项核算。如果产品要跑图，视觉塔的成本要单独按目标仓库重算，本节的数字不适用。

与 Qwen3.5-0.8B 的对照很直接：那边视觉塔 100.59 MMAC 参数、一张 448² 图 81.44 GMAC；这边是 0。但省下的这部分被 24 层全宽 MLP 吃掉了——LFM3 的文本主干比 0.8B 大 1.95 倍，而多模态能力为零。

## 7.2 输出头的形状与共享

| 项 | 数值 |
|---|---:|
| lm_head 形状 | [128000, 2048] |
| MAC | 262,144,000（15.2% token） |
| 权重（MXFP8） | 270.3 MB（15.2% token 带宽） |
| logits 缓冲 | 128,000 × 4 B = 512 KB |
| 与 embedding 共享 | 是，header 里没有 `lm_head.weight` |
| 是否参与 prefill 每个 token | 否，只有最后一个位置 |

共享的收益是容量：省 262.1 M 参数，相当于整模型的 15.2%。代价是量化：`embed_tokens` 做查表时 FP8 完全够用，做 lm_head 时直接决定 top-1，两者只能取高。若 lm_head 必须 FP16，那 270.3 MB 变成 524.3 MB，decode 带宽从 1.782 GB 涨到 2.036 GB，上限从 174 掉到 152 token/s（−12.6%）。

## 7.3 logits 与采样的成本

decode 一个 token 的预算是 5.75 ms（S 较短，310 GB/s），128K 个 logit 的处理能不能压进去，取决于算法：

| 方法 | 比较次数 | 1 GHz 标量核耗时 | 占 token 预算 |
|---|---:|---:|---:|
| 全排序 `std::sort` | 2.18 M | 2.4–4.4 ms | 42–77% |
| `nth_element` / k 堆 | 0.66 M | 0.7–1.2 ms | 12–21% |
| 256 桶直方图 + 二分 | ~0.26 M | <0.3 ms | <5% |

结论是采样必须用部分选择，但紧迫性比 Qwen3.5-0.8B 低：那边 248K 词表全排序要 5–10 ms，是 2.66 ms 预算的 190–380%，直接翻车；这边 2.4–4.4 ms 是预算的 42–77%，虽然吃掉近一半但仍能跑。词表减半是 LFM3 在端侧的一个隐性优势。

工程上还有三条硬约束：温度与 top-p 各要扫一遍 logits（256 桶直方图可合成一遍）；512 KB logits 必须整块留 SRAM，否则两遍读 DRAM；约束解码要把非法 token 的 logit 置 −inf，这又是 128K 次比较。

## 7.4 输出头的坑（速查）

| # | 坑 | 后果 |
|---:|---|---|
| 1 | 把 lm_head 算进 prefill 每个 token | 算力高估 17.9%（262.1 / 1,467.3） |
| 2 | 漏掉 `embedding_norm` | 输出幅度错，形状全对 |
| 3 | 共享权重只按查表量化 | top-1 一致率掉到 80% 以下 |
| 4 | logits 存 FP16 | 128K 维里相邻两个候选的差常在 1e-3 量级，FP16 分不开 |
| 5 | 采样走全排序 | 吃掉 42–77% 的 token 预算 |

# 第 8 章　三本账：算力 / 带宽 / 缓存

每 token 1,729.45 MMAC，其中 MLP 65.5%、lm_head 15.2%、13 层卷积 48.1%、11 层注意力 36.7%（后两项含各自 MLP，与前三项不并列）。每 token 读 1.782 GB 权重，这是 decode 速度的唯一决定因素。缓存是"一小一大"：卷积窗口恒定 0.32 MB，KV 只在 11 层产生且其中 5 层封顶。

## 8.1 算力账（decode，S 较短）

| 组件 | 数量 | 单个 MAC | 小计 | 占比 |
|---|---:|---:|---:|---:|
| 层型 A（卷积，含 MLP） | 13 | 64.01 M | 832.1 M | 48.1% |
| 层型 B（全注意力，含 MLP） | 6 | 57.74 M | 346.5 M | 20.0% |
| 层型 B'（滑窗注意力，含 MLP） | 5 | 57.74 M | 288.7 M | 16.7% |
| 注意力 S 项（S=1） | 11 | 4,112 | 0.045 M | 0.0% |
| lm_head | 1 | 262.14 M | 262.1 M | 15.2% |
| final norm | 1 | 4,096 | 0.004 M | 0.0% |
| **合计（S 较短）** | | | **1,729.5 M** | **100.0%** |
| **S = 4096 时** | | | **1,835.8 M** | |
| **S = 32768 时** | | | **2,543.2 M** | |
| **S = 262144 时** | | | **8,202.3 M** | |

1,729.5 MMAC 折成浮点是 3.459 GFLOP/token。

表里有四件事。

**层数多不等于算力多。** 13 层卷积占 54% 的层数、48.1% 的 MAC；11 层注意力占 46% 的层数、36.7% 的 MAC。按层平均，卷积层 64.01 M 比注意力层 57.74 M 高 10.9%。卷积替代注意力在算力上是**增**的，不是减的。

**原因在 mixer 的宽度，不在算子类型。** 卷积层 mixer 16.78 M，注意力层 mixer 10.49 M，差 6.29 M 全部来自 `in_proj` 的三倍宽（6144 对 q+k+v 的 3072）。MLP 在两种层里完全一样，但占比分别是 73.74% 与 81.74%，所以"换 mixer"只动到层内的 1/4 到 1/5。

**MLP 是全局最大项。** 24 层 1,132.84 M，占 65.5%，比所有 mixer 加门控、RoPE 加起来（334.06 M）多 3.4 倍。优化顺序上它排第一，比任何 mixer 层面的结构创新都重要。

**S 项被压住了。** 5 层滑窗封顶 256，让 S 项从"随 S 线性涨的 11 层"变成"6 层随 S + 5 层常数"。S=256K 时 S 项 6.47 GMAC 仍是固定部分的 3.7 倍，但若 11 层全不封顶会再高 80%。

与 Qwen3.5-0.8B 对照：那边固定部分 767.0 M，S=4096 时 867.7 M；这边 1,729.5 M 与 1,835.8 M。比值 2.25× 与 2.12×，略低于纯文本参数比 2.30×（0.8B 的 873.44 M 里有 100.59 M 视觉塔与 20.45 M MTP 不参与文本 MAC），因为 LFM3 的 S 项占比更低（6.1% 对 11.6%）。

## 8.2 带宽账（decode，MXFP8 = 8.25 bit = 1.031 B/参数）

| 项 | 参数量 | 字节 |
|---|---:|---:|
| 层型 A × 13 | 831.8 M | 857.6 MB |
| 层型 B × 11 | 634.8 M | 654.5 MB |
| lm_head（= embed） | 262.1 M | 270.3 MB |
| final norm | 2,048 | 2.1 KB |
| **合计** | **1,728.8 M** | **1,782.4 MB** |

| 附加流量 | 大小（S=4096） | 说明 |
|---|---:|---|
| KV cache 读 | 50.3 MB | 6 层 × 2,048 B/token × 4096 |
| 滑窗 KV 读 | 2.62 MB | 5 层 × 256 位置，与 S 无关 |
| 卷积窗口读写 | 0.64 MB | 0.32 MB × 2，可常驻 SRAM |
| 激活 | < 1 MB | BCx 12 KB、MLP 中间 15 KB、logits 512 KB |

**速度上限**（310 GB/s）：

```
只看权重：1.782 GB ÷ 310 GB/s = 5.75 ms → 174 token/s
S=4096：  1.836 GB ÷ 310 GB/s = 5.92 ms → 169 token/s
S=32K：   2.188 GB ÷ 310 GB/s = 7.06 ms → 142 token/s
S=256K：  5.006 GB ÷ 310 GB/s = 16.15 ms → 62 token/s
实际效率 60~70%（按 174 的上限）      → 104~122 token/s
```

算术强度 1,729.45 M MAC ÷ 1.7824 GB = **0.970 MAC/B**。Qwen3.5-0.8B 是 0.99，Qwen3.5-2B 是 0.98——三个模型几乎一样，说明"每个权重每 token 用一次"这个约束与模型结构无关。

引擎吞吐下限因此是 310 GB/s × 0.970 = **301 GMAC/s**。这个数比 Qwen3.5-0.8B 的 306 GMAC/s 略低，两者可以共用同一套引擎规格。

LFM3 的权重是 0.8B 的 2.30 倍（1.782 对 0.776 GB），token/s 正好是它的 1/2.30（174 对 400）。上下文变长时 LFM3 掉速更慢：S=4K 时 KV 只占本 token 流量的 2.9%，0.8B 占 6.1%。

## 8.3 缓存账

| 项 | 公式 | S=4K | S=32K | S=256K |
|---|---|---:|---:|---:|
| 卷积窗口（FP16） | 13 × 2048 × 6 × 2B = 319,488 B | 0.32 MB | 0.32 MB | 0.32 MB |
| 全局 KV（6 层，FP16） | 6 × 2 × 4 × 128 × 2B × S = 12,288·S | 50.3 MB | 402.7 MB | 3,221.2 MB |
| 滑窗 KV（5 层，封顶 256） | 5 × 2 × 4 × 128 × 2B × 256 | 2.62 MB | 2.62 MB | 2.62 MB |
| **合计** | | **53.3 MB** | **405.6 MB** | **3,224.2 MB** |

把"如果 24 层都是注意力"的假想 KV 并列进来，省下的量就是卷积层的全部价值：

| 上下文 | 24 层全 attention 的 KV | 实际 KV | 省下 | 省的比例 |
|---|---:|---:|---:|---:|
| 4096 | 201.3 MB | 53.3 MB | 148.0 MB | 73.5% |
| 32768 | 1,610.6 MB | 405.6 MB | 1,205.0 MB | 74.8% |
| 262144 | 12,884.9 MB | 3,224.2 MB | 9,660.7 MB | 75.0% |

三个数要记住。

**第一，SRAM 下限真的降下来了。** 卷积窗口 0.32 MB 意味着片上不再需要为"每层一个固定大状态"预留空间。Qwen3.5-0.8B 必须留 18.87 MB 给 DeltaNet 状态，SRAM 至少 24 MB；LFM3 的固定状态只要 0.32 MB，SRAM 可以按"权重流水的双缓冲 + 一层激活 + 一个滑窗 KV"来定，1.5–4 MB 就够。这是两颗芯片能不能共用 SRAM 方案的分水岭。

**第二，KV 与权重的拐点在 145K。** 1.782 GB ÷ 12,288 B = 145,052 token。超过这个上下文，DRAM 里装的主要是 KV 而不是权重。Qwen3.5-0.8B 的拐点是 63K，2B 是 158K——LFM3 落在两者之间，靠的是"层数 11、词表小"。

**第三，容量账宽松得多。** 4 GB 名义容量扣掉权重 1.78 GB、系统与运行时 0.7 GB，剩 1.52 GB 给 KV，折合 124K token。同样 4 GB 跑 256K 上下文需要 FP8 KV（1.61 GB）才勉强，或者把滑窗层的截断做严格（已经算了）。8 GB 设备上 256K 上下文是宽松的。

三条必须做的设计决策，每条带代价：

1. **滑窗 KV 必须真截断**。按 256 环形缓冲实现，5 层恒为 2.62 MB；照 HF 的 `DynamicCache` 存全长，S=256K 时这 5 层变成 2.68 GB，多 2.68 GB 且没有任何精度收益。代价是两套地址生成器（线性 + 环形）。
2. **KV 用 FP16 还是 FP8**。FP16 在 S=256K 时 3.22 GB；FP8 是 1.61 GB，省 1.61 GB，4 GB 设备才谈得上满上下文。代价是 K 的量化误差直接进 softmax 分母，需要单独验证。
3. **卷积窗口常驻 SRAM 还是落 DRAM**。常驻只要 0.32 MB，落 DRAM 则每 token 多 0.64 MB 流量（+0.04%）但多两次往返，且把唯一的跨 token 依赖变成访存依赖。**必须常驻。**

# 第 9 章　时间线：一个 token 走完全程

## 9.1 Decode 一个 token（S=4096）

```
 1  查表 embed[token_id]                    0 MAC                   DMA     ← 读 4 KB
 2  for layer 0..23:                                                ── 每层 4 个 norm
 3      operator_norm                       4 K MAC                 VPU
 4      ┌ 若为卷积层（13 层）：
 5      │   in_proj (2048→6144)             12.58 M MAC            引擎    ← 读 12.97 MB
 6      │   u = B ⊙ x                       2 K 乘                  VPU
 7      │   conv k=7                        14.3 K MAC + 24.6 KB RMW VPU    ← ═窗口
 8      │   y = C ⊙ v                       2 K 乘                  VPU
 9      │   out_proj                        4.19 M MAC             引擎    ← 读 4.32 MB
10      ├ 若为注意力层（11 层）：
11      │   q/k/v proj                      6.29 M MAC             引擎    ← 读 6.48 MB
12      │   q/k norm                       5.1 K MAC               VPU
13      │   RoPE（64 或 128 维）            2.6 K / 5.1 K MAC       VPU     ← 角度 FP32
14      │   KV 追加                         0 MAC                   DMA     ← 写 2 KB
15      │   Q·Kᵀ + softmax + A·V            16.8 M MAC             引擎/VPU ← 读 KV 8.4 MB
16      │   ⊙ σ(gate)                       2 K 乘                  VPU
17      │   o_proj                          4.19 M MAC             引擎    ← 读 4.32 MB
18      └
19      post_operator_norm                  4 K MAC                 VPU
20      残差加                              2 K 加                  VPU
21      ffn_norm                            4 K MAC                 VPU
22      w1 + w3                             31.46 M MAC            引擎    ← 读 32.4 MB
23      silu(g) ⊙ u2                        7.7 K 乘 + 7.7 K exp    VPU
24      ── DMA 在线量化 ──                  0 MAC                   DMA     ← 读写 15 KB
25      w2                                  15.73 M MAC            引擎    ← 读 16.22 MB
26      post_ffn_norm                       4 K MAC                 VPU
27      残差加                              2 K 加                  VPU
28  final embedding_norm                    4 K MAC                 VPU
29  lm_head                                 262.14 M MAC           引擎    ← 读 270.3 MB
30  采样（温度/top-p/约束）                 ~0.26 M 运算           CPU     ← 见 7.3
```

每 token 的 DRAM 流量是 1.782 GB 权重 + 52.9 MB KV + 0.5 MB logits，合计 **1.836 GB**，除以 310 GB/s 得 **5.92 ms**，对应 169 token/s。

这个时间线里只有两处是跨 token 的：第 7 行（卷积窗口）和第 14 行（KV 追加）。第 7 行是读改写，需要 24.6 KB 的往返；第 14 行是纯写，2 KB。**整个 decode 没有任何一步需要"等上一步的状态算完"超过一拍**——这是 LFM3 与 DeltaNet 系模型最本质的差别，后者的 delta 递推有 5 拍硬串行，且每层要读写 2.1 MB。

## 9.2 Prefill 一段 prompt（S=1024）

同样的算子序列，但 M=1024，全部 GEMV 变 GEMM：

| 项 | 数值 |
|---|---|
| 每 token MAC | **1,467.31 M**（= 1,729.45 − lm_head 262.14；lm_head 只在最后一位算一次） |
| 1024 token 固定部分 | 1,502.5 GMAC |
| 1024 token 的 attention 项 | 17.7 GMAC（因果下三角，全局层 12.95 G 加滑窗层 4.72 G） |
| **总算力** | **1,520.2 GMAC = 3.04 TFLOP** |
| 若系统 25 TOPS（FP8 稠密） | ≈ 122 ms |
| 权重带宽 | 1.782 GB 只读一次（被 1024 个 token 复用） |
| 带宽时间 | 1.782 GB ÷ 310 GB/s = 5.75 ms ≪ 122 ms |
| **结论** | prefill 是**算力瓶颈**，decode 是**带宽瓶颈** |

122 ms 处理 1024 个 token，合 8.4K token/s，是 decode（169 token/s）的 50 倍。Qwen3.5-0.8B 上这个比值是 65 倍，差别来自 LFM3 的 prefill 每 token 算力更高（1,467.3 M 对 512.8 M，2.86 倍）而带宽只高 2.3 倍。

一个 prefill 特有的现象：attention 项只占 1.2%。因为 S=1024 时因果下三角让 QKᵀ 的实际乘加是 P(P+1)/2 而不是 P²，全局层 6 × 2 × 2048 × 524,800 = 12.95 G，看着不小，但相对 1,502.5 G 的固定部分是零头。**prefill 的成本几乎全部在权重矩阵乘上，与上下文长度的关系很弱**——这一点与 decode 正好相反。

## 9.3 视觉前向：本 checkpoint 不适用

没有视觉塔，所以"一张图的前向"退化成"图被编码成多少个 token，就按多少个 prompt token 算"。给一个换算：一张 448² 的图按 2×2 合并得 196 个 token，过本模型主干（不含 lm_head）的成本是 196 × 1,467.31 M = **287.6 GMAC**。

Qwen3.5-0.8B 上同样一张图是 182.0 GMAC（含它自己的视觉塔 81.44 G）。LFM3 若将来接上视觉编码器，光主干这一段就贵 1.58 倍——视觉 token 的成本主要由主干宽度决定，与视觉塔大小关系不大。

# 第 10 章　算子 → 硬件映射

Decode 全程是 M=1 的 GEMV，阵列利用率天然极低，提升空间不在阵列大小，在流水与门控。模型里有两处串行：卷积窗口的读改写与 softmax 归约，但两者都不构成吞吐瓶颈。lm_head 只有 15.2% 带宽，不再是最痛的一项。

## 10.1 分类矩阵

| 类别 | 特征 | 本模型算子 | 归属 |
|---|---|---|---|
| **GEMM / GEMV** | 激活 × 权重 | 全部 `*_proj`、`lm_head`、QKᵀ、AV | 矩阵引擎 |
| **归约** | 沿一维求和/最值 | 97 次 RMSNorm、softmax 分母 | VPU |
| **逐元素** | 同形状逐点 | 门控乘、SiLU、sigmoid、残差、RoPE | VPU |
| **串行递推** | 后步依赖前步 | 卷积窗口左移（6 位置，13 层） | VPU + 状态缓存 |
| **查表** | 索引取行 | `embed_tokens` | VPU / DMA |
| **搬运** | 无计算 | KV 追加、窗口写回、量化 pass | 引擎内部 / DMA |
| **控制流** | 分支/随机数 | 采样、约束解码、停止判断 | CPU |

## 10.2 引擎侧的三条结论

**① Decode 全是 GEMV，算力用不上。**

所有投影加 lm_head 都是 M=1 的矩阵向量乘。1,729.45 MMAC 在 5.75 ms 里跑完，平均 **301 GMAC/s**，25 TOPS 的峰值是 12.5 TMAC/s，利用率 **2.4%**。这个数与 Qwen3.5-0.8B 的 2.3% 几乎一样，说明利用率只由 M=1 决定，与模型结构无关。优化点只有三个：权重流水保持连续、细粒度门控配合 DVFS、别指望把阵列做大。

**② 两处串行，但都不是吞吐瓶颈。**

- 卷积窗口：13 层 × 24.6 KB 的读改写，3 拍（门控 → 卷积 → 门控）。按 128 通道、1 GHz 算，每层 14,336 MAC 是 112 拍，13 层 1,456 拍 ≈ **1.5 µs**。
- Softmax：S=32K 时 6 × 32,768 = 196,608 次 exp，128 通道下 1,536 拍 ≈ **1.5 µs**（滑窗层封顶 256，另加 1,280 次）。

两者合计 3 µs，占 5.75 ms 预算的 **0.05%**。对比 Qwen3.5-0.8B：那边的 delta 递推加状态读写约 50 µs，占 1.9%。**卷积替代注意力在这一项上省了 17 倍**，但两边都不影响吞吐，只影响首字延迟的抖动。

**③ 最大单算子是 MLP，不是 lm_head。**

`w1`+`w3` 并联 31.46 MMAC/层，24 层 755.0 MMAC（43.7%），单层权重 32.4 MB。lm_head 262.1 MMAC（15.2%）只排第二。这与 0.8B 的格局相反——那边 lm_head 是第一大单项（33.1%）。所以 LFM3 的优化顺序应该是：MLP 的 tile 与权重流水 → 注意力的 QKᵀ/AV → lm_head。把 lm_head 降到 FP8 只省 15.2% 的带宽，而在 0.8B 上是 33.8%。

## 10.3 投机解码：没有 MTP，只能外挂草稿

模型没有 MTP 头，所以任何投机加速都要引入第二个模型。设草稿模型 D 个参数（MXFP8 下 1.031·D 字节），接受率 α、草稿长度 γ；下表取 α=0.7。

```
每步流量 = 1.782 GB（主模型验证，一次读）+ γ × 1.031·D
期望产出 = (1 − α^(γ+1)) / (1 − α)
```

| 方案 | 每步流量 | 期望产出 | 净加速 |
|---|---:|---:|---:|
| 无投机 | 1.782 GB | 1.00 | 1.00× |
| γ=2，草稿 0.3 B | 1.782 + 0.62 = 2.40 GB | 2.19 | **1.63×** |
| γ=3，草稿 0.3 B | 1.782 + 0.93 = 2.71 GB | 2.53 | **1.66×** |
| γ=3，草稿 0.15 B | 1.782 + 0.46 = 2.24 GB | 2.53 | **2.01×** |

对比 Qwen3.5-0.8B：它自带 MTP，草稿成本只有 20.45 M 参数（21.1 MB）加共享 lm_head，剪枝到 8K 词表后 γ=3 能到 2.27×。LFM3 要外挂 0.3 B 草稿才能拿到 1.66×，性价比明显低一档。

但 LFM3 在回滚上占优：接受失败时，卷积窗口只要回退 6 个 token 的重放（0.32 MB 快照），KV 按长度截断。Qwen3.5-0.8B 要快照 18.87 MB 的 FP32 递推状态，快照本身就要 37.7 MB 的读写。

若规划投机解码，验证 pass 一次吃 γ+1 个 token，算力 ×(γ+1)。γ=3 时每步 4 × 1,729.45 = 6.92 GMAC，配 2.71 GB 流量，算术强度 2.55 MAC/B，引擎需要 **≥ 791 GMAC/s** 才不成为新瓶颈，比 M=1 的 301 GMAC/s 高 2.6 倍。

# 第 11 章　量化归属

前置约束：矩阵引擎的输入只接受 FP8 / MXFP8，不接受 BF16；输出可以是 FP32 / FP16 / MXFP8。下面按这个约束逐项归属。

LFM3 的量化难点与 Qwen3.5-0.8B 完全不同。那边是"线性注意力的递推状态必须 FP32"，这边没有递推状态；这边的新问题是**卷积的输入已经是两个投影的乘积**，以及**卷积权重每通道只有 7 个值**。

## 11.1 逐项归属

| 组件 | 权重 | 激活/输入 | 输出 | 说明 |
|---|---|---|---|---|
| `embed_tokens` / `lm_head` | MXFP8（待验证） | MXFP8 | FP32 | 共享权重，策略取两者要求高的那个 |
| 卷积 `in_proj` | MXFP8 | MXFP8 | FP32 | 三段用途不同，B/x 进乘法、C 进门控 |
| 卷积 `conv` | **FP16** | **FP16** | FP16 | 每通道 7 个权重，块缩放无意义；跨 token |
| 卷积 `out_proj` | MXFP8 | MXFP8 | **FP32** | 直通后置归一 |
| 门控乘 ① ② | — | **FP16** | FP16 | 乘积重尾，是风险点 |
| 卷积窗口 | — | **FP16** | — | 跨 token 常驻，不量化 |
| 注意力 `q/k/v_proj` | MXFP8 | MXFP8 | FP32→FP16 | |
| `q_norm` / `k_norm` | FP16 | **FP32** | — | 128 维归约 |
| RoPE | — | **FP32** | — | 角度误差 → 相位漂移 |
| `Q·Kᵀ` | — | FP16 | — | 不建议 MX |
| softmax | — | **FP32** | — | 分母动态范围大 |
| `A·V` | — | **FP16**（p 不用 FP8） | — | p 长尾，E4M3 相对误差约 6% |
| 注意力 `gate_proj` | MXFP8 | MXFP8 | **FP16** | 16 个标量，量化收益为零 |
| 注意力 `o_proj` | MXFP8 | MXFP8 | **FP32** | 直通后置归一 |
| MLP `w1`/`w3` | MXFP8 | MXFP8 | **FP16** | 下一步 SiLU |
| MLP SwiGLU | — | **FP16** | — | SiLU 负半轴放大误差 |
| MLP `w2` | MXFP8 | MXFP8（在线量化） | **FP32** | 直通残差 |
| 四个 RMSNorm | FP16 | FP32 统计 | FP16 | 增益是 `w` 不是 `1+w` |

## 11.2 三条硬规则

**残差流永不进 FP8。** 24 层累加，中途只有 4 次归一化，没有重新归一的机会。写残差的 `out_proj`/`o_proj`/`w2` 输出必须 FP32。

**卷积窗口与门控乘永远 FP16。** 窗口是跨 token 的状态，误差会停留 7 个 token；门控乘的输入是乘积，重尾，块缩放会把尾部削掉。这两项合计只占 0.04% 的带宽，抬精度没有成本。

**MXFP8 只用于"激活输入是单变量"的投影。** 本模型的 `in_proj`、`q/k/v/o_proj`、MLP 三个投影都满足（输入是归一化后的激活）。不满足的是卷积的输入（乘积）与门控乘的两个因子。

## 11.3 lm_head 的特殊处理

| 观察 | 数字 |
|---|---|
| 占 decode MAC | 15.2% |
| 占 decode 权重带宽 | 15.2%（270.3 MB/token） |
| 与 embedding 共享 | 是（省 262.1 M 容量，不省带宽） |
| logits 维度 | 128,000 |
| 采样延迟 | 2.4–4.4 ms（全排序），占 5.75 ms 预算的 42–77% |

建议分三步验证。

1. 先做 MXFP8（W8A8），FP32 累加、FP32 输出，测 top-1 token 一致率，门槛 >95%。
2. 不达标就抬到 FP16 权重：lm_head 从 270.3 MB 涨到 524.3 MB，多读 254.0 MB/token，带宽 1.782 GB → 2.036 GB，上限 174 → 152（−12.6%）。
3. 仍不达标则移到 VPU 做 FP16 GEMV。算力上完全可行：262.1 M × 30 token/s = 7.9 GMAC/s = **15.7 GFLOPS**，0.5 TOPS 的 VPU 只用 3.1% 的 duty。

三步的代价都比 Qwen3.5-0.8B 小（那边抬精度是 −25% 速度），因为词表只有一半、权重基数更大。

## 11.4 卷积分支的量化

卷积层是整个模型里最不该激进量化的地方，原因有三个，都能量化。

**第一，卷积的输入是乘积。** `u = B ⊙ x`，两个近似高斯的乘积，超额峰度约 6（单变量为 0）。MXFP8 的 32 元素块共享一个 E8M0 指数，块内若有 1–2 个尾部值，整个块的量化步长被拉大，其余 30 个值的相对误差按 2 的幂跳，等效损失 1–1.5 位有效精度，比单变量激活严重。

**第二，卷积权重每通道只有 7 个值。** `conv.weight` 是 [2048, 1, 7]，沿通道切块时每块 32 个通道 × 7 个抽头 = 224 个值，块内混进了时间维。时间维的 7 个抽头量级差异很大（通常第一个和最后一个最大），块缩放会把它们拉平，等于削掉了卷积的形状。

**第三，误差会在窗口里停留。** 一次量化误差影响 7 个后续 token 的输出，而 MLP 的误差只影响当前 token。同样的误差幅度，卷积层的等效影响是 MLP 的 7 倍。

| 项 | 归属 | 理由 |
|---|---|---|
| `in_proj` | MXFP8 | 输入是归一化激活，单变量 |
| 门控乘 ① | FP16 | 乘积重尾，块缩放削尾 |
| `conv` 权重 | **FP16** | 7 值/通道，块内混时间维；总量只有 14,336 × 13 = 186,368 个参数，MXFP8 下 0.19 MB，抬到 FP16 也只多 0.19 MB |
| `conv` 激活 | **FP16** | 跨 token 停留 7 步 |
| 窗口 | **FP16** | 同上 |
| 门控乘 ② | FP16 | 同 ① |
| `out_proj` | MXFP8 | 输入是门控输出，单变量，进残差前还要归一 |

量化点密度：每个卷积层 3 处（`in_proj` 输出、门控 ① 后、`out_proj` 输出），13 层 39 处；每个注意力层 5 处（q/k/v 输出、p、o_proj 输出），11 层 55 处；加 MLP 24 层 × 2 处 = 48 处。**全模型每 token 142 处量化点，涉及约 30 万元素过 `amax → E8M0 → E4M3` 流水**（BCx 6,144 + MLP 7,680 + 注意力 4,096，按层加总）。这是 0.02% 量级的向量开销，排 pipeline 时不要漏。

## 12.2 与 Qwen3.5-0.8B 方案的资源对比

| 项 | Qwen3.5-0.8B | LFM3-1.7B |
|---|---|---|
| 总参数 | 873.44 M | 1,728.80 M |
| 每 token 权重 | 0.776 GB | 1.782 GB |
| 310 GB/s 下上限 | 400 token/s（实际 225–263） | 174 token/s（实际 104–122） |
| 每 token MAC（S 短） | 767.0 M | 1,729.5 M |
| 算术强度 | 0.99 MAC/B | 0.970 MAC/B |
| 固定跨 token 状态 | 18.87 MB（FP32 递推）+ 0.66 MB | **0.32 MB** |
| KV 每 token | 12.0 KB（6 层） | 22.0 KB（11 层，5 层封顶） |
| S=256K 的 KV | 3.22 GB | 3.22 GB |
| KV 追上权重 | 63K | 145K |
| 串行链 | ~50 µs（1.9%） | ~3 µs（0.05%） |
| 投机解码 | MTP 1 层，γ=3 剪枝后 2.27× | 无，外挂 0.3 B 草稿 1.66× |
| 词表 | 248,320 | 128,000 |
| 采样 / 预算 | 5–10 ms / 2.66 ms | 2.4–4.4 ms / 5.75 ms |
| SRAM 下限 | ≥24 MB | 1.5–4 MB |
| 视觉塔 | 100.59 M | 无 |

最反直觉的一行是"S=256K 的 KV"：两个模型完全一样（3.22 GB），但来源不同。0.8B 是 6 层 × 2 头 × 256 维，LFM3 是 6 层 × 4 头 × 128 维——每层每 token 都是 2 KB，恰好相同。差别在 0.8B 另外还有 18.87 MB 的固定状态，LFM3 没有。

由此得到一条产品结论：**这两颗模型不能共用同一套 SRAM 方案，但可以共用同一个引擎规格。** SRAM 一侧，LFM3 只需要 1.5–4 MB，而 0.8B 必须留 24 MB；按 0.8B 设计的芯片跑 LFM3 是浪费（多出的 20 MB 只能当权重预取缓冲），按 LFM3 设计的芯片跑不了 0.8B。引擎一侧，两者的算术强度差 2%（0.970 对 0.99），下限差 1.6%（301 对 306 GMAC/s），同一个 25 TOPS 的阵列对两者都是带宽受限的。

真正需要为 LFM3 单独设计的有两处：卷积窗口的读改写通路（24.6 KB、跨 13 层，需要一个专用的小状态 SRAM 与小粒度 DMA），以及滑窗 KV 的环形地址生成器。

# 附录 B　复现脚本

纯 Python，无第三方依赖。实测输出写在注释里，与权重文件对差额。

```python
H, I, V = 2048, 7680, 128000
n_h, d_h, n_kv = 16, 128, 4      # 16 头 × 128，4 个 KV 头
K, state = 7, 6                  # kernel 7，窗口 = kernel − 1
L_conv, L_slide, L_full = 13, 5, 6

# 层型 A：双门控短卷积（10 个张量）
A = (4*H                         # operator / post_operator / ffn / post_ffn
     + H*(3*H)                   # in_proj  2048→6144
     + H*K                       # conv     2048×7（depthwise）
     + H*H                       # out_proj 2048→2048
     + 3*H*I)                    # MLP w1 + w3 + w2
print(f"A 单层 = {A:,}")         # 63,985,664

# 层型 B：注意力（14 个张量）
B = (4*H                         # 四个 norm
     + H*(n_h*d_h)               # q_proj   2048→2048
     + 2*H*(n_kv*d_h)            # k_proj + v_proj  2048→512 ×2
     + 2*d_h                     # q_norm + k_norm  128 ×2
     + H*n_h                     # gate_proj 2048→16
     + H*H                       # o_proj   2048→2048
     + 3*H*I)                    # MLP
print(f"B 单层 = {B:,}")         # 57,712,896
print(f"张量数 = {L_conv*10 + (L_slide+L_full)*14 + 2}")   # 286，与 header 一致

tot = V*H + L_conv*A + (L_slide+L_full)*B + H
print(f"total  = {tot:,} ({tot/1e9:.4f} B)")   # 1,728,801,536（1.7288 B）

# 每 token MAC（含逐元素与归约）
A_mac = A + 4*H + (H + H) + (H + H) + I   # norm 多算的 4H、两道门、两个残差、MLP 门控乘
print(f"A MAC  = {A_mac:,}")     # 64,009,728

B_mac = (B + (2*n_h*d_h + 2*n_kv*d_h - 2*d_h)    # q/k norm：5,120 − 256
         + (n_h*d_h + n_h)                       # 每头门：乘 2,048 + sigmoid 16
         + 4*H + 2*H                             # 四个 norm 多算的 4H、两个残差 2H
         + 2560 + I)                             # RoPE（全层）与 MLP 门控乘
print(f"B MAC  = {B_mac:,}")     # 57,742,352（全注意力）/ 57,744,912（滑窗）

fix = L_conv*A_mac + L_full*B_mac + L_slide*(B_mac + 2560) + 2*H + V*H
print(f"fix    = {fix:,} ({fix/1e6:.1f} M)")    # 1,729,453,232（1729.5 M）

w = tot*1.031
print(f"bytes  = {w:,.0f} ({w/1e9:.3f} GB)")    # 1,782,394,384（1.782 GB）
print(f"AI     = {fix/w:.3f} MAC/B")            # 0.970
print(f"tok/s  = {310e9/w:.1f}")                # 173.9

cs = L_conv*H*state*2
print(f"conv_state = {cs:,} B")                 # 319,488
print(f"KV/token   = {(L_full+L_slide)*2*n_kv*d_h*2:,} B")   # 22,528

for S in (4096, 32768, 262144):
    real = L_full*2*n_kv*d_h*2*S + L_slide*2*n_kv*d_h*2*min(S, 256) + cs
    allA = (L_conv+L_slide+L_full)*2*n_kv*d_h*2*S
    print(f"S={S:>6}  actual={real/1e6:8.1f} MB  all-attn={allA/1e6:8.1f} MB  save={(allA-real)/1e6:8.1f} MB")
# S=  4096  actual=    53.3 MB  all-attn=   201.3 MB  save=   148.1 MB
# S= 32768  actual=   405.6 MB  all-attn=  1610.6 MB  save=  1205.0 MB
# S=262144  actual=  3224.2 MB  all-attn= 12884.9 MB  save=  9660.7 MB

print(f"KV 追上权重的上下文 = {w/(L_full*2*n_kv*d_h*2):,.0f}")   # 145,052
# 实测权重文件 3,457,635,448 B，减 8 B 长度前缀与 32,368 B header 后 ÷2
# = 1,728,801,536，与本脚本 tot 的差额为 0（0.0000%）
```

脚本里 `A` 与 `B` 是参数数，`A_mac` 与 `B_mac` 要补上不占参数的计算。卷积层补四项：四个 norm 从 H 抬到 2H（+4H）、两道门控乘（+2H）、两个残差（+2H）、MLP 里 7680 维的门控乘（+I），合计 24,064，正好让 A 从 63,985,664 走到 64,009,728。注意力层补六项：q/k norm 的 20 条 128 维归约（5,120 − 256）、每头门（2,048 乘加 16 个 sigmoid）、四个 norm 的 +4H、两个残差 +2H、RoPE 2,560、MLP 门控乘 7,680，合计 29,456，正好让 B 从 57,712,896 走到 57,742,352。滑窗层比全层多的 2,560 就是 RoPE 多转的 32 对角度（20 个头 × 32 对 × 4 次乘加）。
