# Qwen3-0.6B 逐层计算拆解

2026-10-29 ｜ 依据 `config.json`、权重清单（311 个张量，1,503,300,328 B）、`transformers` 4.51.0 的 `modeling_qwen3.py` 与模型卡核对

## 摘要

Qwen3-0.6B 是纯文本、28 层全注意力的稠密模型。唯一参数 596,049,920，其中 embedding 占 26.1%；checkpoint 里另存了一份与 embedding 同值的 lm_head，所以 header 元素数是 751,632,384。

对芯片设计影响最大的几项：

- decode 每 token 读 **0.6145 GB** 权重（MXFP8），310 GB/s 上限 504.5 token/s；S=4096 降到 285.9，S=32768 只剩 **70.9**。同一带宽下 0.8B 是 400 / 375 / 263。
- KV 每 token **112 KB**，是 0.8B（12 KB）的 9.33 倍。KV 流量在 S=5,358 时追平权重，0.8B 的拐点是 63K。
- 28 层没有一层能省 KV：`sliding_window=null`，无 DeltaNet、无跨层共享、无滑窗。KV 压缩是唯一的结构性手段。
- 每 token 596.59 M MAC，算术强度 0.971 MAC/B，与 0.8B 的 0.99、2B 的 0.98 同档。矩阵引擎下限 301 GMAC/s，一颗引擎可以同时服务三代模型。
- 跨 token 状态为零：没有循环状态、没有 MTP、没有视觉塔。SRAM 地板从 0.8B 的 19.5 MB 降到约 6 MB，省下的预算应该换成 KV 带宽。
- lm_head 占 26.1% 权重带宽和 26.1% 短上下文 MAC；151,936 路 logits 采样要 2.6 M 次比较，与 3.5 ms 的 token 预算同量级。
- prefill 是算力瓶颈：1024 token 40.9 ms（25 TOPS）；32K prompt 的二次项吃掉 81% 算力。
- 0.6B 不是 0.8B 的等比缩小：它用 28 份 KV 换掉了 0.8B 的 18 层固定状态，短上下文快 26%，32K 上下文慢 3.7 倍。

后面按"模型事实、层结构、逐算子、算力与带宽、硬件映射、量化、结论"展开。

# 第 1 章　事实基线

## 1.1 数据来源与核对方法

这份拆解依赖四类材料：镜像站上的 `config.json`；单文件权重 `model.safetensors` 的 header（35,552 B，311 个张量，可读出名字、形状、dtype）；`transformers` 4.51.0 的 `modeling_qwen3.py`；以及官方模型卡。权重不分片，没有 index 文件，所有形状都是 header 原文，不是从 config 推的。

核对有两条独立路径。

第一条是字节数。文件 1,503,300,328 B，减去 8 B 长度字段和 35,552 B header，数据区 1,503,264,768 B，除以 2（311 个张量全是 BF16）得 751,632,384，与 header 元素数之和逐位相同，差额 **0 B**。这个文件没有分片对齐填充，也没有未登记字节。

第二条是逐层求和。28 层每层 15,730,944，合计 440,466,432；加 `embed_tokens` 155,582,464 和 final norm 1,024，得 **596,049,920**。header 多出 155,582,464，正好是 `lm_head.weight` 这一份：`tie_word_embeddings=true`，但 checkpoint 仍然把 lm_head 实体化了一遍，两份张量形状同为 [151936, 1024]。所以"0.6B"指的是去重后的 596.05 M，而文件里躺着 751.63 M 个元素。

这条差额不是对齐误差，是可省掉的 0.1604 GB。转换脚本如果不做去重，flash 里就白放一份词表；如果做了去重又把 embedding 当 lm_head 用，则必须保证量化参数两边一致（见 11.3）。

模型卡的"0.6B 总参数、0.44B 非 embedding"与本文的两个数对得上：440,466,432 就是 0.44B 非 embedding 部分，596,049,920 就是 0.6B 总数。这是第三条旁证。

|---|---|---|
| `modeling_qwen3.py` | L62–L76 `Qwen3RMSNorm` | 确认增益是 `w` 而不是 `1+w` |
| `modeling_qwen3.py` | L144–L167 `eager_attention_forward` | 确认 scaling、softmax 的 FP32 路径、`repeat_kv` |

| `modeling_qwen3.py` | L315–L352 `Qwen3RotaryEmbedding` | 确认 `cat(freqs, freqs)` 与 FP32 角度 |

## 1.2 关键超参

| 项 | 值 | 与 0.8B 的差异 |
|---|---|---|
| `hidden_size` | 1024 | 相同 |
| `num_hidden_layers` | 28 | 0.8B 是 24 |
| `layer_types` | 28 层全部 full attention | 0.8B 是 18 DeltaNet + 6 attention |
| `num_attention_heads` × `head_dim` | 16 × 128 | 0.8B 是 8 × 256 |
| `num_key_value_heads` | 8（GQA 2:1） | 0.8B 是 2（GQA 4:1） |
| `q_proj` 输出宽度 | 2048（= 16 × 128，无门控） | 0.8B 是 4096（Q + 输出门控） |
| `k_proj` / `v_proj` | [1024, 1024] | 0.8B 是 [512, 1024] |
| `o_proj` | [1024, 2048] | 相同 |
| `q_norm` / `k_norm` | [128]，作用在 head_dim | 0.8B 是 [256] |
| `intermediate_size` | 3072（= 3.0 × hidden） | 0.8B 是 3584（= 3.5 × hidden） |
| `hidden_act` | silu（SwiGLU） | 相同 |
| `vocab_size` | 151936 | 0.8B 是 248320 |
| `tie_word_embeddings` | true | 相同，但本模型 checkpoint 仍存了 lm_head |
| `rms_norm_eps` | 1e-6 | 相同 |
| `attention_bias` | false，全模型 0 个 bias | 相同 |
| `attention_dropout` | 0.0 | 相同 |
| `rope_theta` | 1e6 | 0.8B 是 1e7 |
| 旋转维度 | 全部 128 维 | 0.8B 只转 25%（64/256） |
| `rope_scaling` | null（YaRN 需外部配置） | 0.8B 是 mRoPE |
| `max_position_embeddings` | 40960 | 0.8B 是 262144 |
| 原生上下文 | 32768（模型卡）；tokenizer 上限 131072 | 0.8B 是 262144 |
| `sliding_window` / `use_sliding_window` | null / false | 0.8B 无滑窗概念 |
| `max_window_layers` | 28（占位，不生效） | — |
| MTP | 无 | 0.8B 有 1 层 |
| 视觉塔 | 无 | 0.8B 有 100.59 M |

四处值得单独说。

**head 几何没有随 hidden 缩小。** 16 × 128 = 2048 = 2 × hidden，q_proj 的 N 维是 hidden 的两倍；k/v 各 8 × 128 = 1024，恰好等于 hidden。这两组比例决定了一切：投影的 K 维只有 1024，而 KV 的存量由 28 × 8 × 128 决定，与 hidden 无关。

**GQA 从 4:1 退到 2:1。** 0.8B 每个 KV 头服务 4 个 Q 头，这里只服务 2 个。同样的 1024 hidden，这里的 KV 更宽：每层每 token 是 8 头 × 128 维 × 2（K+V）= 2048 个数，0.8B 单层只有 2 头 × 256 × 2 = 1024 个数；前者是后者的 2 倍，再乘层数 28 对 6，总量差 9.33 倍。

**RoPE 是全维的。** 128 维全部旋转，不像 0.8B 只转 64 维；频率表 `cat(freqs, freqs)` 复制一遍，配对是 `(i, i+64)` 的 half-split。`rope_theta` 从 1e7 降到 1e6，低频波长缩短 10 倍，32K 位置上的相位分辨率更紧。

**MLP 相对变窄。** `intermediate_size / hidden` 从 0.8B 的 3.5 降到 3.0，单层 MLP 从 11.01 M 降到 9.44 M。小模型上反而收窄 MLP，是这一代 0.6B 与 0.8B 在参数分配上的主要差别。

# 第 2 章　模型全景

## 2.1 一个子模型

```
Qwen3-0.6B ─── 文本主干 596.05 M ─┬─ 28 × 全注意力层    440.47 M
                                  ├─ embed_tokens       155.58 M
                                  └─ final norm           1,024
                （checkpoint 另存 lm_head 155.58 M，与 embed 同值）
```

没有视觉塔、没有 MTP、没有投机头。decode 和 prefill 用的是同一套 596.05 M 参数，唯一的阶段差异是 lm_head 只在最后一个位置算。这与 0.8B 的三子模型结构（文本 752.39 + 视觉 100.59 + MTP 20.45）形成直接对照：0.8B 的 873.44 M 里有 13.9% 在纯文本 decode 时根本用不到，本模型没有这部分容量负担。

无视觉塔带来的另一个结果是 prefill 形状单一：不会出现 196 个视觉 token 与文本 token 混合的序列，也不用为图像单独准备 784 行的 GEMM tile。

## 2.2 文本主干的层型配比

| 层型 | 层数 | 每层参数 | 每层 MAC（S→0） | 结构特征 |
|---|---:|---:|---:|---|
| A　全注意力层（含 MLP） | 28 | 15.73 M | 15.75 M | q/k/v/o 四投影 + qk-norm + 全维 RoPE + KV + SwiGLU |
| **合计** | **28** | | **441.00 M** | 28 层固定项 |

层内配比是 40.0% 参数在 attention、60.0% 在 MLP，28 层一致。

28 层完全同构，比 0.8B 的 3:1 混合简单得多。选择全 attention 的代价全部落在缓存上：每层每 token 4 KB KV，28 层 112 KB。0.8B 用 18 层 DeltaNet 把历史压进 18.87 MB 固定状态，换来每 token 12 KB 的 KV；本模型没有这个选项，因为 0.6B 规模下再加一份 19 MB 的 FP32 状态，SRAM 预算会比权重还紧张。

对硬件有一个直接好处：28 层形状完全相同，一份测试向量、一套 tile 划分、一份 DMA 描述符可以覆盖全部。0.8B 需要两套（DeltaNet 与 attention），验证工作量大约翻倍。

## 2.3 计算形态的四个类别

| 类别 | 特征 | 本模型里的算子 | 典型维度 |
|---|---|---|---|
| 稠密矩阵乘（GEMM / GEMV） | 激活 × 权重 | 四投影、MLP 三投影、lm_head、QKᵀ、A·V | K = 1024 或 2048 或 3072，N = 1024…3072 |
| 归约 | 沿一维求和或求最值 | RMSNorm、q/k norm、softmax | 1024 / 128 / S |
| 逐元素 | 同形状逐点 | SiLU、门控乘、残差、RoPE 旋转、scaling | 任意 |
| 串行递推 | 后一步依赖前一步 | 无 | — |

本模型没有真正的递推状态，四类里第四类为空。softmax 沿 S 归约是串行的，但它每一步只依赖当前层的 score，不跨 token 保留状态，性质与 DeltaNet 的 5 拍递推不同：前者可以用 online softmax 折进流式读取，后者必须把整个状态读改写一遍。

外加两个非计算类别：查表（embedding，每 token 一次）和搬运（KV 追加与回读，每 token 112 KB 写、4,096·S B 读）。搬运量在 S=5,358 时超过全部权重，这是第 8 章的主线。

## 3.2 层的通用骨架

```
x [1,1024]
 │
 ├─► [G0] input_layernorm ─► r [1,1024]
 │                             │
 │                             ▼
 │                       y = Attn(r) [1,1024]      ← 层型 A（3.3）
 │                             │
 └─ x = x + y ◄────────────────┘                  ← 残差 ①，唯一写回 x 的点
 │
 ├─► [M1] post_attention_layernorm ─► r2 [1,1024]
 │                             │
 │                             ▼
 │                       z = MLP(r2) [1,1024]      ← 子模块 M（3.4）
 │                             │
 └─ x = x + z ◄────────────────┘                  ← 残差 ②
 │
输出 x [1,1024]（形状与输入完全相同）
```

**读图约定（第 3 章所有 DAG 通用）**

| 记号 | 含义 |
|---|---|
| `─►` / `──►` | 同 token 内的数据依赖，箭头上带计算 |
| `┄` / `┄┄►` | 纯视图（view / reshape / transpose），0 MAC，只改索引与 stride |
| `═` / `══►` | 跨 token 状态读写（K cache / V cache） |
| `[G0]` `[G1]` … | 并行组：同组内互不依赖，可并发发射；组号小的必须先完成 |
| 横向分支 | 只表示并行关系，不表示时间先后；汇合点之前的所有分支都必须就绪 |

层内只有三种形状变换：

| 变换 | 形状关系 | 例子 | 通道语义 |
|---|---|---|---|
| 稠密线性 | `[K] → [N]` | `q_proj` 1024→2048、`gate_proj` 1024→3072 | 全部通道混合，每个输出 = 全 K 维内积 |
| 逐元素 / 逐通道 | `[N] → [N]` | RMSNorm 缩放、SiLU、门控乘、残差加、RoPE | 一进一出，通道对齐 |
| 纯视图 | `[N] → [M₁]…[Mₖ]`（∏Mᵢ = N） | `view(16,128)`、`transpose(1,2)` | 不改数，只改索引 |

残差流宽度恒为 1024，与 0.8B 相同。所以两模型的逐元素、归一、残差开销完全一样，差别只在投影宽度与层数。

## 3.3 层型 A：Qwen3 全注意力层（28 层）

Mixer 共 6 个张量，加骨架 2 个 norm：

| 张量 | 形状 | 作用 |
|---|---|---|
| `self_attn.q_proj` | [2048, 1024] | 16 个 Q 头 × 128 维 |
| `self_attn.k_proj` | [1024, 1024] | 8 个 KV 头 × 128 维 |
| `self_attn.v_proj` | [1024, 1024] | 同上 |
| `self_attn.o_proj` | [1024, 2048] | 16 头拼回 2048 维再压到 1024 |
| `self_attn.q_norm` | [128] | 按 head_dim 归一，在 RoPE 之前 |
| `self_attn.k_norm` | [128] | 同上 |
| `input_layernorm` / `post_attention_layernorm` | [1024] | 骨架自带 |

相对 0.8B 的 attention 层，多出三件事：

1. **q/k norm 作用在 128 维的头上**，不是 1024 维的残差流上。16 个 Q 头各做一次，8 个 KV 头各做一次，共 24 条 128 宽归约。
2. **全维 RoPE**，128 维全部旋转，64 对角度；0.8B 只转 64 维中的前 64 维（实际是 256 维里的 64 维）。
3. **KV 写 4 KB/token/层**，0.8B 写 2 KB。

### 3.3.1 计算流（decode 单 token，依赖 DAG）

```
x [1,1024] ──► [G0] input_layernorm ──► r [1,1024]
                                          │
        ┌─────────────────────────────────┼─────────────────────────────────┐
        ▼                                 ▼                                 ▼
 [G1] q_proj                        [G1] k_proj                       [G1] v_proj
      [1,2048]                           [1,1024]                          [1,1024]
        │                                 │                                 │
   view(16,128) ┄                    view(8,128) ┄                     view(8,128) ┄
        │                                 │                                 │
        ▼                                 ▼                                 ▼
 [G2] q_norm                        [G2] k_norm                     [G2] 写 V cache
        │                                 │                          ═══► v [8,S,128]
        ▼                                 ▼                                 │
 [G3] RoPE(全 128 维)               [G3] RoPE(全 128 维)                    │
        │                                 ▼                                 │
        │                          [G3] 写 K cache                         │
        │                          ═══► k [8,S,128]                        │
        ▼                                 │                                 │
 [G4] Q·Kᵀ ◄══════════════════════════════┘                                 │
```

### 3.3.3 关键路径与并行机会

- 关键路径：`G0 → G1(q) → G2(q_norm) → G3(RoPE) → G4(Q·Kᵀ) → G5(softmax) → G6(A·V) → G7(o_proj) → G8 → G9 → G10 → G11 → G12 → G13`，14 级。28 层串起来是 **392 级依赖**，这是 decode 无法靠并行绕开的深度。
- K/V 两条支路不延长路径，但 G4 必须等 K 写完、G6 必须等 V 写完。V 支路只有一次投影加一次搬运，是最早就绪的；K 支路多一次 norm 和一次 RoPE，比 V 晚两拍。
- G10 的 gate/up 是唯一一对完全对称的并行算子，共享同一个 1024 维输入，可以合并成一次 `1×1024×6144` 的发射。
- 单层 32.59 M MAC（S=4096）里，QKᵀ + A·V 占 51.5%，四个投影占 19.3%，MLP 占 29.0%。**attention 的 S 项在这里第一次超过权重项**，这是与 0.8B 最本质的算力差异：0.8B 的 767 M 里 S 项只占 11.6%（S=4096）。
- 顺序性约束有三处不能重排：`q_norm` 必须在 transpose 之前、RoPE 必须在写 K cache 之前、`o_proj` 必须在 16 头拼回之后。

# 第 5 章　通用算子库

全模型只用 5 个通用算子：RMSNorm、按头 RMSNorm、因果 softmax、SiLU/SwiGLU、全维 RoPE。后面 28 层都是这几个算子的排列组合。

它们都上不了矩阵引擎：RMSNorm 是行内归约，softmax 是沿 S 归约加超越函数，RoPE 是跨 lane 置换，按头 RMSNorm 是 24 条 128 宽的小归约。四条量化边界需要记住：Qwen3 的增益是 `w` 不是 `1+w`；q/k norm 的归约维是 128 不是 1024；softmax 必须在 FP32 里做；RoPE 角度必须 FP32、位置 id 必须整数。

decode 一个 token 的调用次数：归一 **729 次**（28 层 × 2 + final 1 + 28 层 × 24 个头级 norm），softmax 448 次（28 层 × 16 头），SwiGLU 28 次，RoPE 28 次 × 24 头。0.8B 的归一调用是 397 次，softmax 只有 48 次。

## 5.1 RMSNorm（标准版，不是 zero-centered）

**作用**：按行归一化，再乘一个可学习的逐通道增益。
**公式**：

```
y_i = x_i · rsqrt(mean(x²) + ε) · w_i,   ε = 1e-6
```

**形状**：`[1,1024] → [1,1024]`，归约维 1024。
**MAC**：2 × 1024 = 2,048（平方和一次、缩放一次）。28 层 × 2 + final 1 = 57 次/token，合计 116,736 MAC。
**精度**：平方和在 FP32 里累加，1024 个 FP16 平方直接相加会损失约 3 位；归一后的值降回 FP16。
**归属**：VPU，1024 宽加法树。
**坑**：

1. **增益是 `w`，不是 `1+w`。** 这是与 Qwen3.5 系列最容易踩反的一处：0.8B 的 RMSNorm 是 zero-centered（乘 `1+w`），Qwen3 是标准 T5 风格（乘 `w`）。两代模型的权重不能共用同一个打包脚本，否则本模型整层输出被压到接近 0，而且不会报形状错误。
2. 归约宽度 1024，一条 1024 宽加法树约 10 级流水。它出现在每层入口和 MLP 入口，是流水线的固定开销。
3. final norm 与 28 层的 norm 是同一算子，硬件复用同一单元。

## 5.2 按头 RMSNorm（q_norm / k_norm）

**作用**：在 RoPE 之前，对每个 head 的 128 维做归一。这是 Qwen3 相对 Qwen2 的主要结构变化，作用是稳定 attention logits 的尺度。
**公式**：

```
q̂_{h,i} = q_{h,i} · rsqrt(mean_{d=0..127}(q_{h,d}²) + 1e-6) · w_i
```

**形状**：q `[1,16,128]`、k `[1,8,128]`，24 条归约，每条 128 宽。
**MAC**：2 × 128 × 24 = 6,144。
**精度**：归约 FP32，输出 FP16；`w` 只有 128 个值，被 16 个 Q 头共用。
**归属**：VPU。24 条 128 宽归约可以完全并行，但输出必须按头顺序拼回。
**坑**：

1. 归约维是 **128**，不是 1024。按整行归一会得到完全不同的数值，形状却仍然对得上。
2. 必须在 `transpose(1,2)` 之前做。源码里 `q_norm(self.q_proj(x).view(...,-1,128)).transpose(1,2)`，顺序反了归一的轴就错了。
3. 必须在 RoPE 之前。先旋转再归一会把旋转后的成对结构破坏掉。
4. `w` 只有 128 个值，要保证 16 路广播；不要每个头各读一份权重。

## 5.3 因果 softmax

**作用**：沿 S 维归一化 attention 分数。
**公式**：

```
p_t = exp(α·s_t − m) / Σ_{j≤t} exp(α·s_j − m),   α = 1/√128 = 0.088388
```

**形状**：`[1,16,1,S] → [1,16,1,S]`。
**MAC**：16·S（每个分数一次：比较、exp、累加、除法合并计 1）。S=4096 时 65,536/层，28 层 1.83 M；S=32768 时 524,288/层，28 层 14.68 M。
**精度**：必须 FP32。源码是 `softmax(attn_weights, dim=-1, dtype=torch.float32).to(query.dtype)`，中间不落 FP16。
**归属**：VPU，沿 S 的流水归约。
**坑**：

1. **scaling 是 1/√128 = 0.088388**，不是 1/16。0.8B/2B 的 head_dim 是 256，常数是 0.0625；共用一套常数会在 32K 上把 logits 放大约 1.41 倍。
2. scaling 在 matmul 之后、mask 之前。折进 Q 的投影权重只会改变舍入，但折进 exp 之外的非线性变换就错了。
3. decode 时是 16 条长度为 S 的归约，行最大值与指数和必须一起算（online softmax）；分两遍读 score 会让 S 相关的访存翻倍。
4. S=32K 时单层 16 头 × 32K 个分数，exp 次数 524,288，必须用 LUT 或分段多项式，标量 SFU 跟不上。

## 5.4 SiLU / SwiGLU

**作用**：MLP 的门控激活。`silu(x) = x·sigmoid(x)`。
**公式**：

```
h = silu(W_gate·r2) ⊙ (W_up·r2)
y = W_down·h
```

**形状**：`[1,1024] → [1,3072] ⊙ [1,3072] → [1,1024]`。
**MAC**：门控乘 3,072/层，28 层 86,016。SiLU 本身算一次超越函数，28 层 86,016 次 exp。
**精度**：FP16。SiLU 负半轴把误差放大，E4M3 在负半轴的相对误差可达 6%，会毁掉小激活。
**归属**：VPU。
**坑**：

1. 门控乘在 SiLU 之后、down 之前，顺序反了语义就变。
2. 3072 是 1024 的 3 倍，逐元素单元按 3072 宽设计。0.8B 是 3584（3.5 倍），两模型的逐元素宽度不同，不要共用同一个配置寄存器。
3. LUT 按 FP16 索引算，16K 项 × 16 bit = 32 KB，两模型可共用。

## 5.5 全维 RoPE

**作用**：给 Q/K 注入位置信息。128 维全部旋转，64 对。
**公式**：

```
θ_i = pos / 1e6^(2i/128),   i = 0..63
q'_i      = q_i      · cos θ_i − q_{i+64} · sin θ_i
q'_{i+64} = q_{i+64} · cos θ_i + q_i      · sin θ_i
```

**形状**：q `[1,16,S,128]`、k `[1,8,S,128]`；`cos/sin [S,128]`，后 64 项与前 64 项相同（源码 `cat(freqs, freqs)`）。
**MAC**：每对 4 次乘加。q 是 16 × 64 × 4 = 4,096，k 是 8 × 64 × 4 = 2,048，合计 6,144/层/token，28 层 172,032。
**精度**：角度在 FP32 里算（`freqs = inv_freq @ position_ids`，默认 dtype float32），算完降到模型 dtype；旋转本身 FP16 可接受。
**归属**：VPU，跨 lane 置换网络加三角函数。
**坑**：

1. **half-split，不是 interleaved。** `rotate_half` 把 128 维劈成前后两半再配对：`(q_0, q_64)、(q_1, q_65)…`。按 interleaved 实现不会报错，只会让模型答非所问。
2. `pos` 必须是整数。FP16 在 4096 位置的 ulp 是 4，在 32768 位置是 32，用 FP16 存位置 id 会直接把相邻 token 映射到同一位置。
3. `rope_theta=1e6`，不是 1e4 也不是 0.8B 的 1e7。低频分量 i=63 的波长是 1e6^(126/128) ≈ 8.1e5，对应周期约 5.1e6 token，32K 内几乎不转；高频分量 i=0 的周期是 2π token。两者对相位误差的敏感度差近 6 个数量级，不能统一降精度。
4. cos/sin 表不要按 131072 位置预存：1024 个数 × 4 B × 131072 = 537 MB。现算每 token 128 对 sin/cos，约 2 µs。
5. 写进 cache 的 K 必须是已旋转的。若先写后转，每次读 KV 都要重算，S=32K 时相当于每层多算 32K 次旋转。

### A⑯ 实现/测试坑（按优先级）

1. **RMSNorm 乘成 `1+w`。** 从 Qwen3.5 移植过来的打包脚本最容易带这个假设，后果是 28 层输出全部被压小，top-1 完全错乱。
2. **q_norm 在 transpose 之后做。** 归一轴从 128 变成 S，形状依然对得上，数值全错。
3. **RoPE 用 interleaved。** 配对从 `(i, i+64)` 变成 `(2i, 2i+1)`，短上下文下 loss 只涨一点，长上下文直接崩。
4. **scaling 用 1/16。** 沿用 0.8B 的常数，attention logits 放大约 1.41 倍，softmax 更尖。
5. **`repeat_kv` 物理复制。** 8 → 16 的复制如果落成真实内存，KV 读取翻倍，32K 时多搬 3.76 GB。
6. **KV cache K/V 混精度。** K 用 FP8、V 用 FP16 会让 p 的分布偏斜，长上下文下误差累积。
7. **位置 id 用 FP16。** 4096 以上 ulp ≥ 4，相邻 token 位置相同，RoPE 失效且不报错。
8. **把 3072 当 1024 的整数倍切 tile。** 3072 = 3 × 1024，按 512 切正好 6 份，按 1024 切 3 份，不要引入尾部。

## 6.2 KV cache 与长上下文

### 6.2.1 KV cache 三档

| 上下文 | 每层 | 28 层合计 | 与权重流量之比（0.6145 GB） |
|---|---:|---:|---:|
| 4096 | 16.8 MB | 0.470 GB | 76.4% |
| 32768 | 134.2 MB | 3.758 GB | 611.5% |
| 131072 | 536.9 MB | 15.03 GB | 2446% |

每 token 每层写 4 KB（K 和 V 各 2 KB），读 4,096·S B。**权重小并不让 KV 变轻，反而让它变重**：0.8B 上 S=32K 时 KV 只占权重流量的 51.9%，这里占 611.5%。原因有两个，层数 28 对 6（4.67 倍），KV 头 8 对 2（4 倍），乘起来 18.7 倍；0.8B 的 KV 每 token 12 KB，这里 112 KB，实际差 9.33 倍，因为 0.8B 的 head_dim 是 256。

### 6.2.2 每 token 的 KV 读写

| 项 | 公式 | S=4096 | S=32768 |
|---|---|---:|---:|
| 写 | 28 × 4 KB | 112 KB | 112 KB |
| 读 | 114,688·S B | 0.470 GB | 3.758 GB |
| 读写合计 | | 0.470 GB | 3.758 GB |
| 占 token 总流量 | | 43.3% | 85.9% |

写只有 112 KB，可以忽略；读是全部。S=4096 时 KV 已经吃掉 43% 的 token 预算，S=32K 时 86%。这不是"长上下文才需要注意"的问题，4096 就已经是主项。

### 6.2.3 引擎准入：QKᵀ 与 A·V 的分界

decode 时 QKᵀ 的形状是 `[16, 1, 128] × [16, S, 128]`，M=16、K=128、N=S。矩阵引擎的行利用率是 16/阵列行数。若阵列 128 行，利用率 12.5%；S 越大，K 维读取越连续，越值得上引擎。

| S | 单层 QKᵀ MAC | 单层 KV 读 | 建议 |
|---:|---:|---:|---|
| 1 | 2,048 | 4 KB | VPU，引擎行浪费 87.5% |
| 512 | 1.05 M | 2.1 MB | 临界，看引擎最小 tile |
| 4096 | 8.39 M | 16.8 MB | 引擎，带宽支配 |
| 32768 | 67.1 M | 134.2 MB | 引擎，必须与 softmax 流水重叠 |

分界点不是算力，而是"引擎启动开销 vs 一次 GEMV 的时间"。S 小于 512 时，KV 读取只有 2 MB，引擎的配置与同步开销占主导，放 VPU 更稳。

### 6.2.4 十个必须记住的坑（按危害排序）

1. **28 层全存 KV，没有一层可省。** 任何"某些层可以滑窗"的假设都会让 32K 的容量估算少算 28 层的全部或部分。
2. **`repeat_kv` 按 16 头读。** 8 个 KV 头服务 16 个 Q 头，硬件各读一份，32K 时 KV 带宽从 3.758 GB 变 7.516 GB。
3. **softmax 用 FP16。** 32K 时行最大值与指数和都在 FP16 边界上，分母溢出会直接产生 NaN。
4. **p 量化到 FP8。** p 的质量集中在 [0, 1/S]，E4M3 在 denormal 区相对误差 6%，加权平均不会抵消系统偏差。
5. **KV 长度按 32768 硬编码。** tokenizer 上限是 131072，config 的 `max_position_embeddings` 是 40960，三个数不一致，按最紧的分配会浪费，按最松的分配会溢出。
6. **RoPE 在 KV 写入之后做。** 写进 cache 的必须是已旋转的 K。
7. **q_norm 在 transpose 之前漏做。** 源码顺序是 proj → view → q_norm → transpose → RoPE，少一步不会报错。
8. **attention scaling 放在 softmax 之后。** α 必须在 exp 之前乘。
9. **把 K 和 V 的 cache 做成同一块连续内存。** 两者写入时机差两拍，分开分配才能让 V 提前写。
10. **忘了 lm_head 那 151,936 行。** 它不在 28 层里，但每 token 要读 160.4 MB，占带宽 26.1%。

### M3 SwiGLU 门控

`silu(g) ⊙ u`，3,072 次乘加 + 3,072 次 exp，VPU，FP16。

### M4 down 投影

| 项 | 内容 |
|---|---|
| 形状 | `[1,3072] → [1,1024]` |
| MAC | 3,145,728（33.3%） |
| 归属 | 矩阵引擎，MXFP8 |
| 精度 | 输出 FP32，直通残差 |
| 坑 | K=3072 是层内最长的 K 维，权重 3.24 MB，突发长度最大 |

### M5 残差加

`[1,1024]`，1,024 MAC，VPU。

### M6 MLP 合计与硬件含义

| 项 | 每层 | 28 层 |
|---|---:|---:|
| MAC | 9,440,256 | 264,327,168 |
| 权重带宽（MXFP8） | 9.73 MB | 272.43 MB |
| 占每 token 总量 | 单层 MAC 的 59.9%；token MAC 的 44.3%、带宽的 44.3% | 同 |
| 算术强度 | 0.970 MAC/B | 同 |

MLP 是模型里最大的单一计算块：28 层 264.33 M MAC，占 token 的 44.3%。形状规整——K 固定 1024，N 固定 3072（gate/up）或 1024（down）——tile 只有一种合理切法：N 方向按 512 切 6 份，K 方向整块进。

和 0.8B 比，MLP 的绝对量略小（9.44 M 对 11.01 M，减 14%），但占比更高（44.3% 对 34.5%），因为 0.8B 的 lm_head 占比更大（33.1%）把它压下去了。两模型的 MLP 算术强度都是 0.97，这部分可以直接复用同一套 tile 与精度策略。

## 6.4 层型 D：不存在（无 MTP）

本模型没有投机头。这对第 10.3 节的收益估算有直接影响：0.8B 可以用现成的 20.45 M MTP 头做草稿，草稿成本是 21.1 MB 权重；本模型要做同样的事，必须外挂一个独立草稿模型，草稿成本按它自己的参数量全额计，且不含在本模型的 596.05 M 里。

输出头本身的成本放在第 7 章，它是本模型唯一一个"不在 28 层里、却每 token 都要走"的算子。

# 第 7 章　输出头与采样

## 7.1 没有视觉塔

| 子模型 | 参数 | 参与 decode | 参与 prefill |
|---|---:|:---:|:---:|
| 文本主干 | 596.05 M | 是 | 是 |
| 视觉塔 | 0 | — | — |
| MTP / 草稿头 | 0 | — | — |
| **合计** | **596.05 M** | | |

0.8B 的 873.44 M 里有 121.04 M（视觉 100.59 + MTP 20.45）在纯文本 decode 时不参与，占 13.9%。本模型没有这部分，容量与首字延迟都少一块。代价是投机解码与多模态都没有现成抓手，要用就得外挂（见 10.3）。

## 7.2 lm_head 的形状与算法

| 项 | 数值 |
|---|---:|
| 形状 | [151936, 1024] |
| MAC | 155,582,464 |
| 权重（MXFP8） | 160.4 MB |
| 算术强度 | 0.970 MAC/B |
| logits 缓冲 | 151,936 × 4 B = 607,744 B |
| 与 embedding 共享 | 逻辑是，物理存了两份 |

这是一个 K=1024、N=151936 的极扁 GEMV。N 是 K 的 148.4 倍，权重读取完全无法复用，每 token 一次全量读。它的算术强度与层内投影相同（0.97），所以它不改变整模型的带宽性质，只是把总量加了 26.1%。

## 7.3 输出头的成本（三档 S）

| 项 | S→0 | S=4096 | S=32768 |
|---|---:|---:|---:|
| MAC 占比 | 26.1% | 14.6% | 3.6% |
| 占权重带宽 | 26.1% | 26.1% | 26.1% |
| 占总 DRAM 流量 | 26.1% | 14.8% | 3.7% |
| 权重字节 | 160.4 MB | 160.4 MB | 160.4 MB |
| logits 缓冲 | 608 KB | 608 KB | 608 KB |

占权重带宽恒定 26.1%，占总流量与 MAC 占比随 S 稀释。这解释了为什么长上下文下优化 lm_head 的收益下降，但永远不会归零：S=32K 时它仍是 160.4 MB，占 4.37 GB 的 3.7%。

## 7.4 采样：151,936 路 logits

采样是 CPU 上的活，但它的延迟与 token 预算同量级。decode 的预算是 3.498 ms（S=4096），151,936 个 logit 的全排序要 `n log₂n ≈ 2.6 M` 次比较，在 1 GHz 标量核上约 3–6 ms。

| 方法 | 比较次数 | 1 GHz 耗时（估） | 占 3.5 ms 预算 |
|---|---:|---:|---:|
| 全排序 `std::sort` | 2.6 M | 3–6 ms | 86–171% |
| `nth_element` / k 堆 | 0.55 M | 0.6–1.2 ms | 17–34% |
| 256 桶直方图 + 二分 | 0.30 M | <0.4 ms | <11% |

结论：**必须用部分选择**。全排序在 S=4096 时就能吃掉整个 token 预算。0.8B 的词表是 248,320，全排序要 4.5 M 次比较、5–10 ms，对 2.66 ms 的预算占 190–380%，比本模型更严重；本模型的词表小 38.8%，采样压力相对轻，但量级相同。

## 7.5 输出头的坑

1. **以为 tie 就只有一份。** header 里 `lm_head.weight` 与 `embed_tokens.weight` 都在，各 155,582,464 个元素。转换时去重可以省 0.1604 GB，但要注意量化参数必须共用。
2. **logits 用 FP16 存。** 151,936 个值在 FP16 下的排序与 argmax 会在接近的候选间抖动；采样缓冲用 FP32，607,744 B 可以接受。
3. **lm_head 量化到 MXFP8 后不测长尾。** top-1 一致率是门槛，top-5 排序的稳定性也要测，因为采样不是 argmax。
4. **把 final norm 漏掉。** 它在 28 层之外，1024 宽归约，2,048 MAC，很容易在算账时被并进 lm_head。
5. **采样与停止判断串行。** 停止条件（eos、最大长度）要在采样前判，否则白跑一次 160.4 MB。

## 7.6 与 0.8B、2B 的输出头对比

| 项 | 2B | 0.8B | 0.6B |
|---|---:|---:|---:|
| 词表 | 248,320 | 248,320 | 151,936 |
| lm_head 形状 | [248320, 2048] | [248320, 1024] | [151936, 1024] |
| MAC | 508.56 M | 254.28 M | 155.58 M |
| 权重（MXFP8） | 0.524 GB | 0.262 GB | 0.1604 GB |
| 占 token 带宽 | 27.0% | 33.8% | 26.1% |
| logits 缓冲 | 993 KB | 993 KB | 608 KB |
| 全排序比较次数 | 4.5 M | 4.5 M | 2.6 M |

2B → 0.8B 时 hidden 减半，lm_head 也减半，占比反而从 27.0% 涨到 33.8%；0.8B → 0.6B 时词表从 248,320 降到 151,936，占比回落到 26.1%。**词表是唯一不随 hidden 缩放的维度**，它决定了输出头在三代模型里的占比曲线。

# 第 8 章　三本账：算力 / 带宽 / 缓存

每 token 596.59 M MAC，其中 MLP 44.3%、四个投影 29.5%、lm_head 26.1%。每 token 读 0.6145 GB 权重（MXFP8），S=4096 时再读 0.470 GB KV，S=32K 时读 3.758 GB。缓存是"全都要"：没有任何固定状态，全部开销都随 S 线性增长。

## 8.1 算力账（decode，S 较短）

| 组件 | 数量 | 单个 MAC | 小计 | 占比 |
|---|---:|---:|---:|---:|
| 28 层固定项（投影 + MLP + 归一） | 28 | 15.75 M | 441.0 M | 73.9% |
| 层内 S 项（QKᵀ + A·V + softmax） | 28 | 4,112·S | 115,136·S | 随 S 涨 |
| lm_head | 1 | 155.58 M | 155.6 M | 26.1% |
| final norm | 1 | 2,048 | 2,048 | 0.0% |
| **合计（S→0）** | | | **596.6 M** | |
| **S = 4096** | | | **1,068.2 M** | |
| **S = 32768** | | | **4,369.4 M** | |
| **S = 131072** | | | **15,687.7 M** | |

596.59 M MAC 折成浮点口径是 1.193 GFLOP/token。

三个观察。

MLP 是最大的计算块，28 层 264.33 M，占 44.3%。形状最规整，优化它最省力，但它只贡献 44.3% 的带宽——算力与带宽的重心第一次分开。

lm_head 是第二大的单个算子，155.58 M，占 26.1%。它只随 hidden 线性缩放，而层内参数随 hidden 平方缩放；词表从 248,320 降到 151,936 才把它压回 26.1%，若沿用 0.8B 的词表会是 36.6%。

层内 S 项在 S=4096 时已经占 44.1%，S=32K 时占 86.3%。这是与 0.8B 最根本的差别：0.8B 的 18 层 DeltaNet 没有 S 项，S=4096 时 S 项只占 11.6%，所以它的算力账在长上下文下几乎不变；本模型完全由 S 支配。

## 8.2 带宽账（decode，MXFP8 = 8.25 bit = 1.031 B/参数）

| 项 | 参数量 | 字节 |
|---|---:|---:|
| 28 层 | 440.5 M | 0.4541 GB |
| lm_head | 155.6 M | 0.1604 GB |
| final norm | 1,024 | 0.001 MB |
| **合计** | **596.0 M** | **0.6145 GB** |

| 附加流量 | 大小（S=4096） | 说明 |
|---|---:|---|
| KV cache 读 | 0.470 GB | 28 层 × 8 头 × 128 × 4096 × 2 × 2 B |
| KV cache 写 | 112 KB | 每 token 追加，可忽略 |
| 激活 | < 64 KB | 不含 logits 缓冲（608 KB，见 7.2） |

**速度上限**（310 GB/s）：

```
只看权重：0.6145 GB ÷ 310 GB/s = 1.982 ms → 504.5 token/s
S=4096：  1.0843 GB ÷ 310 GB/s = 3.498 ms → 285.9 token/s
S=32768： 4.3726 GB ÷ 310 GB/s = 14.105 ms → 70.9 token/s
实际效率 60~70%        → 短上下文 303~353 / 4K 172~200 / 32K 43~50
```

对比 0.8B：每 token 0.776 GB，短上下文上限 400 tok/s，S=32K 时 263 tok/s。本模型权重少 20.8%，短上下文快 26.2%，S=32K 反而慢 3.7 倍。

算术强度是 596.59 M ÷ 0.6145 GB = 0.971 MAC/B，0.8B 是 0.99，2B 是 0.98。三者的差别不到 3%，原因相同：hidden 缩小，激活与权重同步缩小。但加上 KV 之后，本模型的算术强度在 S=4096 是 0.985，S=32K 是 0.999，**始终不超过 1 MAC/B**。这是纯 attention 架构的性质：KV 的每个字节只被一次乘加使用，和权重一样没有复用。

## 8.3 缓存账

| 项 | 公式 | S=4K | S=32K | S=131K |
|---|---|---:|---:|---:|
| KV（FP16） | 114,688·S B | 0.4698 GB | 3.7581 GB | 15.0324 GB |
| 权重（MXFP8，常驻） | 614,527,468 B | 0.6145 GB | 0.6145 GB | 0.6145 GB |
| **合计（不含工作区）** | | **1.0843 GB** | **4.3726 GB** | **15.6469 GB** |

三个必须做的设计决策。

**一是把 KV 的读取当成主数据通路，不是附属。** 单层看，KV 在 S=3,960 时追平该层权重（16.218 MB）；整 token 看，拐点在 **S=5,358**（0.6145 GB ÷ 114,688 B）。0.8B 的拐点是 63K，相差 11.8 倍。这意味着本模型的 DRAM 调度要按"权重流 + KV 流"双流设计，两条流的比例从 1:0.76（4K）变到 1:6.1（32K）。

**二是 4 GB 设备能跑的上下文比 0.8B 少一个数量级。** 扣掉权重 0.61 GB、系统与运行时 0.7 GB，剩 2.7 GB 给 KV：FP16 下 23,542 token，FP8 下 47,084。0.8B 在同样约束下是 211K。本模型的"原生 32K"在 4 GB 设备上靠 FP16 KV 装不下，必须 FP8（见 11.4）。

**三是 SRAM 地板降到 6 MB 量级。** 没有循环状态，常驻的只有 0.64 MB 激活与 logits。剩下的需求来自 KV 流的分块：按 512 token 分块，单块 K+V 是 8 头 × 512 × 128 × 2 B × 2 = 2 MB，双缓冲 4 MB，加权重与激活 2 MB，合计约 6 MB。0.8B 需要 20 MB，两者的 SRAM 需求差 3 倍多，方向却相反：0.8B 要容量放状态，本模型要带宽放 KV。

## 9.1 Decode 一个 token（S=4096）

```

 2  for layer 0..27:
 3      RMSNorm                             2 K MAC                 VPU
 4      q/k/v proj                          4.19 M MAC             引擎    ← 读 4.32 MB
 5      q_norm / k_norm                     6 K MAC                 VPU
 6      RoPE                                6 K MAC                 VPU
 7      KV 追加                             0 MAC                   DMA     ← 写 4 KB
 8      Q·Kᵀ                               8.39 M MAC             引擎    ← 读 K 8.39 MB
 9      softmax(FP32)                      65.5 K MAC              VPU     ← 沿 S 归约
10      A·V                                8.39 M MAC             引擎    ← 读 V 8.39 MB
11      o_proj                             2.10 M MAC             引擎    ← 读 2.16 MB
12      残差加                             1 K 加                  VPU
13      RMSNorm                            2 K MAC                 VPU
14      gate/up proj                       6.29 M MAC             引擎    ← 读 6.49 MB
15      silu(g) ⊙ u                        3072 次 exp             VPU
16      ── DMA 在线量化 ──                  0 MAC                   DMA     ← 读写 24 KB
17      down proj                          3.15 M MAC             引擎    ← 读 3.24 MB
18      残差加                             1 K 加                  VPU

20  lm_head                                155.58 M MAC           引擎    ← 读 160.4 MB
21  采样（温度/top-p/抽样）                2.6 M 运算              CPU     ← 见 7.4
```

每 token 的 DRAM 流量是 0.6145 GB 权重 + 0.470 GB KV + 1 KB 激活，合计 **1.0843 GB**。除以 310 GB/s 得 **3.498 ms**，对应 285.9 token/s 的上限。

层内的时间分布和 MAC 分布相反：第 8、9、10 行总共 16.84 M MAC、16.78 MB KV，读 KV 的时间是 54.1 µs；第 4、11、14、17 行的权重读取是 16.22 MB，52.3 µs。**一次 attention 的 KV 读取已经和整层所有权重一样贵**，而这还只是 4096 上下文。

## 9.2 Prefill 一段 prompt

同样的算子序列，但 `M = S`，GEMV 变成 GEMM，attention 多出 S² 项。线性项按每 token 441.0 M（= 596.59 − lm_head 155.58）算，二次项按因果 attention 57,344·S² 算（28 层 × 2 个矩阵 × 16 头 × 128 维 ÷ 2）。

| 项 | S=1024 | S=4096 | S=32768 |
|---|---:|---:|---:|
| 线性项（441.0 M × S） | 451.6 GMAC | 1,806.4 GMAC | 14,450.8 GMAC |
| 二次项（57,344·S²） | 60.1 GMAC | 962.1 GMAC | 61,572.4 GMAC |
| **合计** | **511.7 GMAC** | **2,768.5 GMAC** | **76,023.2 GMAC** |
| 折 TFLOP | 1.02 | 5.54 | 152.05 |
| 25 TOPS 下时间 | 40.9 ms | 221.5 ms | 6,081.9 ms |
| 权重带宽时间（只读一次） | 1.98 ms | 1.98 ms | 1.98 ms |
| 二次项占比 | 11.7% | 34.7% | 81.0% |

Prefill 是算力瓶颈，decode 是带宽瓶颈。1024 token 时算力时间是带宽时间的 20.7 倍；32K prompt 时二次项占到 81%，算力时间 6.08 s，是权重读取的 3,072 倍。这就是为什么阵列要按 prefill 定尺寸，而 decode 只用到它的 2.4%（见 10.2）。

对照 0.8B：1024 token 的 prefill 是 525.1 GMAC、42 ms，本模型是 511.7 GMAC、40.9 ms，几乎相同。prefill 的线性项由参数量决定，两者都在 0.6–0.8B 量级，所以这一项不构成选型差异。差异全在长 prompt 的二次项：0.8B 只有 6 层 attention 有 S² 项，本模型 28 层全有，同样的 32K prompt，本模型的二次项是 0.8B 的 4.67 倍。

# 第 10 章　算子 → 硬件映射

Decode 全程是 M=1 的 GEMV（除 QKᵀ 的 M=16），阵列利用率天然低。本模型的特殊之处不在算力，而在两处：28 个 softmax 串行点，以及 KV 流在 4K 就超过权重。

## 10.1 分类矩阵

| 类别 | 特征 | 本模型算子 | 归属 |
|---|---|---|---|
| **GEMM / GEMV** | 激活 × 权重矩阵 | 四投影、三个 MLP 投影、lm_head、QKᵀ、A·V | 矩阵引擎 |
| **归约** | 沿一维求和/最值 | RMSNorm、q/k norm、softmax 分母、amax | VPU |
| **逐元素** | 同形状逐点 | silu、sigmoid、exp、门控乘、残差、RoPE | VPU |
| **串行递推** | 后步依赖前步 | 无 | — |
| **查表** | 索引取行 | embed_tokens | VPU / DMA |
| **搬运** | 无计算 | KV cache、量化 pass、swizzle | DMA |
| **控制流** | 分支/随机数 | 采样、停止判断 | CPU |

与 2.3 的四类一一对应，唯一的空格是"串行递推"。0.8B 在这一格里有 18 层 delta 更新，是它延迟地板的主要来源；本模型把这一格换成了 28 个 softmax 归约，性质从"状态依赖"变成"长度依赖"。

## 10.2 引擎侧的三条结论

**① Decode 全是 GEMV，算力用不上。**

每 token 1.068 G MAC 在 3.498 ms 里跑完，平均 305 GMAC/s；25 TOPS 的峰值是 12.5 TMAC/s，利用率 **2.4%**。S=32K 时 4.369 G / 14.105 ms = 310 GMAC/s，利用率 2.5%——几乎不变，因为 KV 的算术强度也是 1 MAC/B，加长上下文不会提高算力利用率。

所以优化点只有三个：权重流与 KV 流都要保持连续，别让每个 tile 重新握手；细粒度门控配合 DVFS，decode 时 97% 的阵列空闲；不要把阵列做大，做大只对 prefill 有意义。

**② 28 个 softmax 串行点，是流水线深度的来源。**

每层 16 条长度为 S 的归约，28 层共 448 条。S=4096 时 1.835 M 次 exp，128 lane 的 SFU 在 1 GHz 下约 14.3 µs；S=32K 时 14.68 M 次，约 114.7 µs，占 14.105 ms 的 **0.8%**。

绝对值不大，但它是纯串行：softmax 不结束，A·V 不能开始；A·V 不结束，o_proj 不能开始。28 层串起来的关键路径是 392 级（14 级 × 28 层）。按每级 0.5 µs 的同步与发射开销算，光调度就 196 µs，占 4K 预算的 5.6%。所以真正的约束不是算力，而是"能否把下一层的权重预取与当前层的 softmax 重叠"。

对照 0.8B：它只有 6 个 softmax 点，但有 18 层 × 5 拍 = 90 拍 delta 递推。本模型的串行点是 28 个 softmax（含 QKᵀ/AV 共 84 级），0.8B 是 6 个 softmax 加 90 拍递推，两者总深度同量级，性质不同：本模型的串行段可以用 online softmax 折进 KV 流式读取，0.8B 的递推必须把 1 MiB 状态读改写。

**③ lm_head 加采样，仍是头部瓶颈。**

lm_head 占 26.1% 带宽、26.1% 短上下文 MAC，单算子最大。输出 151,936 维 logits，608 KB 缓冲；采样全排序 2.6 M 次比较、3–6 ms，与 3.498 ms 的 token 预算同量级。

比 0.8B 轻：0.8B 的 lm_head 占 33.8% 带宽，全排序 4.5 M 次、5–10 ms，对 2.66 ms 的预算占 190–380%。词表从 248,320 降到 151,936，把这一项从"第一瓶颈"压回"第二瓶颈"。

## 10.3 没有 MTP 时的加速手段

Decode 是带宽瓶颈，根因是每个权重每 token 只用一次。能提高复用次数的办法只有三类：

| 手段 | 复用倍数 | 代价 | 净收益 |
|---|---|---|---|
| Batching（多用户） | ×B | 端侧通常 B=1 | — |
| 外挂草稿模型（无 MTP） | 理想 1/(1−p_acc)；100 M 草稿、γ=3 时 1.69× | 草稿权重 + 验证算力 ×4 | 1.64~1.69× |
| KV 量化到 FP8 | KV 流量减半 | 长上下文精度风险 | S=32K 时 1.75× |
| 增大 KV 长度 | 无 | 流量线性涨 | 负收益 |

草稿成本必须算进去。假设外挂一个 100 M 参数的草稿模型（这是设计假设，不是本模型的组件），单 token 接受率 p_acc=0.70（同为假设），MXFP8 下每草稿 token 读 0.1031 GB，E = (1−p_acc^(γ+1))/(1−p_acc)：

```
γ=2：B_step = 0.6145 + 2×0.1031 = 0.8207 GB，E=2.19 → 2.19×0.7487 = 1.64×
γ=3：B_step = 0.6145 + 3×0.1031 = 0.9238 GB，E=2.53 → 2.53×0.6652 = 1.69×
```

算力侧还有一个约束：验证 pass 一次吃 γ+1 个 token，γ=3 时每步 4 × 596.59 M = 2.386 G MAC，配 0.9238 GB 流量，算术强度 2.58 MAC/B，引擎需要 **≥801 GMAC/s** 才不成为新瓶颈，是 M=1 下限 301 GMAC/s 的 2.66 倍。

0.8B 有现成的 20.45 M MTP，草稿路径 21.1 MB；本模型没有，必须外挂并单独训练，这是选型时要先确认的一条。KV 量化的收益更确定：S=32K 时 KV 从 3.758 GB 降到 1.879 GB，tok/s 从 70.9 升到 124.3，比任何投机手段都直接（见 11.4）。

# 第 11 章　量化归属

前置约束：矩阵引擎的输入只接受 FP8 / MXFP8，不接受 BF16；输出可以是 FP32 / FP16 / MXFP8。下面按这个约束逐项归属。

## 11.1 逐项归属

| 组件 | 权重 | 激活/输入 | 输出 | 说明 |
|---|---|---|---|---|
| embed_tokens | BF16/FP8 常驻 | — | — | 0 MAC，只查表；与 lm_head 共享 |
| `q_proj` | MXFP8 | MXFP8 | FP16 | 输出进 q_norm |
| `k_proj` / `v_proj` | MXFP8 | MXFP8 | FP16 | 决定 KV 存量精度 |
| `q_norm` / `k_norm` | FP16 | FP16 | FP16 | 归约 FP32 |
| **RoPE** | — | **FP32 角度** | FP16 | 位置 id 必须整数 |
| **K/V cache** | — | FP16（可 FP8） | FP16 | 见 11.4 |
| **Q·Kᵀ** | — | FP16 | **FP32** | score 误差被 softmax 放大 |
| **softmax** | — | **FP32** | FP16 | 分母动态范围大 |
| **A·V** | — | **p 用 FP16** | FP16 | p 不建议 FP8 |
| `o_proj` | MXFP8 | MXFP8 | **FP32** | 直通残差 |
| 残差流 | — | FP32 | FP16 | 28 层累加，不量化 |
| `gate_proj` / `up_proj` | MXFP8 | MXFP8 | FP16 | 下一步 silu |
| **SwiGLU** | — | **FP16** | FP16 | silu 负半轴放大误差 |
| `down_proj` | MXFP8 | MXFP8（运行期在线量化） | **FP32** | 直通残差 |
| final norm | FP16 | FP16 | — | 归约 FP32 |
| **lm_head** | MXFP8（待验证） | MXFP8 | **FP32** | 见 11.3 |

## 11.2 三条硬规则

**残差流永不进 FP8。** 误差跨 28 层累加，中途没有重新归一的机会，写残差的投影输出必须是 FP32。本模型比 0.8B 多 4 层累加，这一条更硬。

**KV 的 K 与 V 必须同精度，softmax 必须 FP32。** K 参与 QKᵀ 后进 exp，误差被指数放大；V 参与加权平均，误差被平均稀释。两者精度不一致会让 p 的分布偏斜，长上下文下表现为"复读"而不是数值溢出。

**MXFP8 输出只在链式 GEMM 之间考虑。** 本模型每个投影后面都接了非线性或归约，没有链式 GEMM，所以 v1 只需要 FP32 和 FP16 两档输出。

## 11.3 lm_head 的特殊处理

| 观察 | 数字 |
|---|---|
| 占 decode MAC（短上下文） | 26.1% |
| 占 decode 权重带宽 | 26.1%（0.1604 GB/token） |
| 与 embedding 共享 | 逻辑是，物理存两份 |
| logits 维度 | 151,936 |
| 采样延迟 | 3–6 ms（全排序），超过 3.5 ms 预算 |

建议分三步验证。

1. 先做 MXFP8（W8A8），FP32 累加、FP32 输出，测 top-1 token 一致率，门槛 >95%。
2. 不达标就把 lm_head 提到 FP16 权重：lm_head 从 0.1604 GB 涨到 0.3112 GB，每 token 从 0.6145 GB 涨到 0.7653 GB，tok/s 从 504.5 降到 **405.1**（−19.7%）。
3. 仍不达标则把 lm_head 移到 VPU 做 FP16 GEMV。算力上完全可行：155.6 M × 30 tok/s = 4.67 GMAC/s = **9.3 GFLOPS**，0.5 TOPS 的 VPU 只用 1.9% 的 duty。

第 2 步的代价比 0.8B 小：0.8B 按同一口径从 400 掉到 298.6（−25.3%），本模型从 504.5 掉到 405.1（−19.7%）。因为 lm_head 的占比低（26.1% 对 33.8%），抬精度的惩罚也小。

共享权重还有一个隐性代价：量化策略必须同时满足查表和 lm_head 两个用途。查表对精度要求低，lm_head 要求高，两者冲突只能取高。

## 11.4 KV cache 的量化

KV 是本模型唯一值得大动的一笔缓存，因为它从 4K 起就是主流量。

| 方案 | 每 token | S=32K 总量 | S=32K tok/s | 4 GB 可用上下文 | 风险 |
|---|---:|---:|---:|---:|---|
| FP16（基线） | 112 KB | 3.758 GB | 70.9 | 23,542 | 无 |
| FP8 E4M3 | 56 KB | 1.879 GB | 124.3 | 47,084 | 长上下文 PPL 上升 |
| INT4 | 28 KB | 0.940 GB | 199.5 | 94,168 | 明显退化，不建议 |

三档的算法是同一个式子：`tok/s = 310 GB/s ÷ (0.6145 GB + KV 字节)`。FP8 把 KV 减半，S=32K 时流量从 4.3726 GB 降到 2.4935 GB，速度提升 1.75 倍；S=4096 时从 1.0843 GB 降到 0.8495 GB，提升 1.28 倍。上下文越长，收益越大。

实现上有四处必须单独处理：

| 项 | 归属 | 理由 |
|---|---|---|
| K 的量化 | 每头独立 scale | K 是 post-RoPE，不同频率通道的动态范围差 5 个数量级，per-tensor scale 会被低频通道主导 |
| V 的量化 | 每 token 独立 scale | V 是 pre-RoPE 的值，逐通道分布稳定，逐 token 足够 |
| 首末层 | 保持 FP16 | 第 0 层与第 27 层的 attention 输出直接决定残差流起点与终点，误差没有后续层平均 |
| softmax 输入 | 反量化后进 FP32 | 不要在 FP8 域里做 exp |

不建议 W4A4 KV：p 的加权平均不改善相对精度，4 bit 的 K 在 32K 上的相位误差会累积成系统性偏移。0.8B 上同样的 FP8 KV 操作在 32K 只省 0.201 GB（12 KB → 6 KB），本模型省 1.879 GB，收益差 9.3 倍。

# 第 12 章　对芯片设计的结论与待验证清单

## 12.1 九条结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | decode 每 token 读 0.6145 GB 权重，310 GB/s 理论上限 504.5 tok/s，实际 303–353 | 8.2 |
| 2 | 加长上下文就换瓶颈：S=4096 上限 285.9，S=32K 只剩 70.9，KV 占流量 85.9% | 8.2 / 8.3 |

## 12.2 与 0.8B 方案的资源对比

| 项 | 0.8B | 0.6B |
|---|---|---|
| 结构 | 18 DeltaNet + 6 attention | 28 attention |
| 每 token 权重 | 0.776 GB | 0.6145 GB |
| 短上下文 tok/s | 400 | 504.5 |
| S=4096 tok/s | 375 | 285.9 |
| S=32K tok/s | 263 | 70.9 |
| 每 token MAC（S→0） | 767.05 M | 596.59 M |
| KV 每 token | 12 KB | 112 KB |
| S=32K KV | 0.403 GB | 3.758 GB |
| 固定状态 | 19.5 MB（18.87 + 0.66） | 0 |
| SRAM 地板 | ≥20 MB | 约 6 MB |
| KV 追平权重的拐点 | 63K | 5.36K |
| lm_head 带宽占比 | 33.8% | 26.1% |
| 4 GB 设备可用上下文 | 211K | 23.5K（FP16）/ 47K（FP8） |
| 视觉塔 / MTP | 100.59 M / 20.45 M | 无 |

最反直觉的一条：**文本主干参数少 20.8%，短上下文快 26.2%，32K 上下文慢 3.7 倍。** 0.8B 用 18 层 DeltaNet 把历史压进 19 MB 固定状态，每 token 只付 12 KB；本模型把历史全摊在 28 层 KV 里，每 token 付 112 KB。参数省下来的容量，被缓存成倍还了回去。

由此得到产品结论：两颗模型可以共用同一颗芯片，但不能共用同一套内存策略。引擎规格按 prefill 定，两者算术强度都是 0.97–0.99，同一套阵列够用；SRAM 要按 0.8B 的 20 MB 配，因为本模型多出来的 SRAM 也用不上；KV 带宽要按本模型的 3.76 GB@32K 配，因为 0.8B 的 KV 流量小、不会浪费。两者不冲突：SRAM 是容量问题，KV 是带宽问题，可以在同一颗芯片上分开满足。

真正需要为本模型单独设计的是两处：KV 的分页与 FP8 通路（决定 32K 能不能在 4 GB 设备上跑），以及 151,936 路采样的部分选择（决定 3.5 ms 预算能否成立）。

# 附录 B　复现脚本

纯 Python，无第三方依赖。三个 `print` 段分别是参数、MAC、字节与带宽；注释是真实运行输出。

```python
# Qwen3-0.6B 参数、MAC、字节复现（纯 Python，无第三方依赖）
H, I, V, L = 1024, 3072, 151936, 28
n_h, n_kv, d_h = 16, 8, 128

# 单层 11 个张量
q    = H * (n_h * d_h)        # q_proj       [2048, 1024]
kv   = 2 * H * (n_kv * d_h)   # k_proj+v_proj [1024, 1024] × 2
o    = H * (n_h * d_h)        # o_proj       [1024, 2048]
attn = H + q + kv + o + 2 * d_h + H
mlp  = 3 * H * I
layer = attn + mlp
body  = L * layer
emb   = V * H
uniq  = body + emb + H
ckpt  = uniq + emb            # header 里 lm_head 又存了一份

print(f"q_proj  {q:>14,}")     # q_proj       2,097,152
print(f"attn    {attn:>14,}")  # attn         6,293,760
print(f"mlp     {mlp:>14,}")   # mlp          9,437,184
print(f"layer   {layer:>14,}") # layer       15,730,944
print(f"body    {body:>14,}")  # body       440,466,432
print(f"emb     {emb:>14,}")   # emb        155,582,464
print(f"uniq    {uniq:>14,}")  # uniq       596,049,920
print(f"ckpt    {ckpt:>14,}")  # ckpt       751,632,384

# 单层单 token MAC（decode，S 为上下文）
nrm   = 2 * H                          # RMSNorm，2 MAC/元素
qkn   = 2 * d_h * (n_h + n_kv)         # q_norm/k_norm，按 head
rope  = 4 * (d_h // 2) * (n_h + n_kv)  # 每对 4 MAC
fixed = (nrm + q + kv + o + qkn + rope
         + H + nrm + 2 * H * I + I + H * I + H)
s_term = 2 * n_h * d_h + n_h           # QK^T + AV + softmax 的每 S 系数
lm = V * H
print(f"fixed   {fixed:>14,}")         # fixed       15,750,144
print(f"s_term  {s_term:>14,}")        # s_term           4,112
print(f"28L     {fixed*L:>14,}")       # 28L        441,004,032
print(f"lm      {lm:>14,}")            # lm         155,582,464
for S in (0, 4096, 32768, 131072):
    print(f"S={S:<7}{fixed*L + lm + nrm + s_term*L*S:>15,}")
# S=0          596,588,544
# S=4096     1,068,185,600
# S=32768    4,369,364,992
# S=131072  15,687,694,336

# 权重字节、KV、带宽上限
bp = 1.031
wb = uniq * bp
kv_tok = 2 * n_kv * d_h * 2 * L
print(f"weights {wb:>15,.0f}")         # weights     614,527,468
print(f"kv/tok  {kv_tok:>14,}")        # kv/tok          114,688
print(f"ai      {(fixed*L+lm+nrm)/wb:>14.3f}")   # ai      0.971
print(f"t/s     {310e9/wb:>14.1f}")    # t/s         504.5
for S in (4096, 32768, 131072):
    b = wb + kv_tok * S
    print(f"S={S:<6}{b/1e9:>8.4f} GB {b/310e9*1e3:>8.3f} ms {310e9/b:>6.1f} t/s")
# S=4096    1.0843 GB    3.498 ms  285.9 t/s
# S=32768   4.3726 GB   14.105 ms   70.9 t/s
# S=131072 15.6469 GB   50.474 ms   19.8 t/s
print(f"bytes   {8+35552+2*ckpt:>15,}")  # bytes    1,503,300,328
```

与权重文件的核对：header 元素数 751,632,384 × 2 B + 8 B 长度字段 + 35,552 B header = 1,503,300,328 B，与 `x-linked-size` 逐字节相同，差额 **0 B（0.0000%）**。该文件没有分片对齐填充。去重后的逻辑参数 596,049,920 与 header 相差 155,582,464，这一份全部来自重复存储的 `lm_head.weight`，不是计算误差。
