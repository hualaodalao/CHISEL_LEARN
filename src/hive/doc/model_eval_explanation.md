# model_eval 设计说明

本文解释 model_eval 的建模边界、抽象分工和主要取舍。操作步骤见[入门教程](model_eval_tutorial.md)与[操作指南](model_eval_howto.md)；精确字段和公式见[建模规范与接口参考](model_eval_spec.md)；Qwen3-0.6B 的逐阶段代码、循环和调用关系见[端到端代码导读](model_eval_end2end.md)。

## 1. L0 与 L1 是两种分析视角

L0 回答的是总量问题：在给定模型、工作点、格式和硬件峰值下，全部 MAC 与全部 DRAM 字节分别需要多少理想时间。它用两个标量进入 roofline，因此计算简单、便于检查模型来源和机器平衡，但无法表达 tile、任务依赖、私有 SRAM、端口冲突或未知服务。

L1 回答的是结构问题：一个模型被分解为哪些逻辑算子和原子任务，这些任务在显式拓扑和执行计划下受到哪些依赖、资源与容量约束。它保留更细的数据流和未知项，代价是输入更多、结果解释更复杂，也仍不等于逐周期硬件仿真。

两者因此不是必须先执行 L0、再执行 L1 的流水线。L1 可以独立展开和调度，L0 仅在报告中提供同输入参考。由于流量、工作量和覆盖范围不同，跨层数值不天然构成严格上下界关系，也不能用 `max(L1,L0)` 修补差异。

## 2. 语义、结构需求与数值服务分离

一个可解释的硬件成本需要经过三次转换：

1. **语义**定义算什么，例如 GEMM 形状、softmax 向量和依赖关系；
2. **结构需求**定义硬件要发出多少命令、窗口、拍和端口字节；
3. **数值服务**将结构需求除以有来源的速率，得到秒或周期。

这种分离使形状账和速率证据可以独立审查。命令数正确并不意味着延迟已知；反之，一个声明的 TOPS 数字也不能证明某种形状能按峰值执行。速率未知时保留 None，比用假设填满时间表更能暴露证据缺口。

这也是报告同时保留 semantic/useful/issued/padded/masked MAC、logical/physical bytes 和 excluded costs 的原因。它们描述不同对象，不能为了得到单一“效率”而混为一个指标。

## 3. lowering 与 scheduler 负责不同决策

lowering 将模型语义转换成 LogicalOp、PrimitiveTask、tensor 和依赖。一个逻辑算子是否包含多个 GEMM、VPU、CPU 或 DMA 任务，属于这一层的决策。自定义 lowering 可以改变分解方式，但必须维护数据覆盖、显式转换和数学一致性。

scheduler 不决定算法分解。它面对固定 TaskGraph，在候选实例上执行确定性预约，处理依赖、引擎占用、共享带宽、local 端口、私有容量和 buffer 生命周期。

把二者分开有两个直接收益：

- 同一任务图可以比较不同拓扑和执行计划，而不必重写模型语义；
- 同一拓扑可以评估不同 lowering，而不会让调度器暗中改变算法。

相应的限制也很明确：系统不会自动发现最优分解、自动拆分单个 GEMM、自动融合或自动搜索 SRAM 计划。多实例只有在图中已有可并行任务且资源允许时才有意义。

## 4. 显式 tensor base/view 使数据流可验证

仅按 tensor 名称追踪依赖会误判共享存储。两个 view 可能访问同一 base 的不同区域，也可能覆盖同一元素；reshape 和 stride 会进一步改变名称与元素之间的直觉关系。

因此 L1 以 base 的实际元素区域判断写入覆盖和生产者关系。消费者需要的元素必须由祖先任务写入，无序重叠写入被拒绝，独立 disjoint writer 则可以共存。BufferPlan 同样按 base 建立唯一分配，避免 view 重复占用容量。

这种设计让补齐、转换和跨域副本成为可见任务，而不是隐藏在字节公式中。代价是自定义图更冗长：调用者必须提供 padded backing、完整写入和正确依赖，不能只声明逻辑形状。

## 5. 拓扑与执行计划必须显式声明

硬件 profile 中的核心数是峰值元数据，不是自动并行许可证。默认 L1 只启用一个 active core，每类引擎一个实例，避免把声明核心数直接乘成可达吞吐。

Topology 描述“有哪些物理实例、资源和内存域”，ExecutionPlan 描述“权重和激活如何移动与驻留”，BufferPlan 描述“分配何时获得和释放”。三者分开后，容量与生命周期可以独立于任务成本审查。

私有 SRAM 不跨核池化，DRAM 带宽也不随 active core 数自动复制。跨核访问需要显式 DMA，这使通信端口和未覆盖的跨域路由保持可见。resident、stage 或 overlap 超出容量时直接暴露约束，比自动降级或缩 tile 更容易复现和比较。

## 6. actual、服务预算与条件投影不能合并

`known_service_budget_s` 是任务局部已知成本之和。它适合对账工作量，但既没有扣除可并行部分，也没有加入未知服务，所以不是端到端延迟。

`makespan_s` 是所有必需服务已知、固定计划可完成时的 actual 排程跨度。它包含依赖与资源等待，但仍是分析模型的结果，不是 RTL 实测。

`projection_makespan_s` 用于在部分服务未知时研究已知预算下的调度结构。未知阶段只保留其已知部分，其他依赖、实例、端口、带宽和容量约束仍然生效。这能回答“如果暂不计这些未知服务，固定计划如何预约”，却不能回答真实硬件需要多久。

将 actual 与 projection 分开，避免了两种常见误导：把未知当成零，以及把条件投影当成实测并行证据。两套结果因此拥有各自的时刻、关键路径归因、资源 busy 和内存峰值。

## 7. 未知与阻断是结果的一部分

性能模型并不总能给出时间。特殊函数、转换、混合精度累加、CPU 算法、handoff 或跨域路由缺少服务证据时，未知本身应当进入报告。

未知与阻断也不相同：

- actual 未知而 projection 可用，表示已知预算下仍能完成预约；
- 两者都未知，可能来自容量、分配、布局或候选实例约束；
- blocked 表示当前固定图与计划不可完成，不表示所有可能实现都不可部署。

这种结果比统一填入零或任意惩罚值更适合架构早期分析，因为它把“模型算出很小”与“模型缺少输入”区分开来。代价是报告不一定提供单一吞吐数字，使用者必须阅读 excluded costs 和 blocked constraints。

## 8. DMA handoff 边界避免重复计费

非 DMA 的跨引擎依赖可能包含同步与可见性成本，因此目标任务可带通用 handoff 阶段。未提供 `sync_us` 时该阶段未知，显式零只代表一个零成本场景。

涉及 DMA 的依赖不添加同一通用 handoff，因为显式 DMA 已描述搬运及其端口服务，再添加通用费用可能重复计费。这个例外不表示 DMA 同步免费；跨 core route、可见性和其他未建模服务仍分别保留未知。

该边界体现了同一原则：成本应归属于可审查的任务或阶段，而不是同时隐藏在多个通用规则中。

## 9. 来源与有效性标志限制结论强度

manifest、命名输入和来源指纹用于重现“这份报告由哪些输入和代码生成”。它们不是完整依赖闭包，也不是结果内容哈希，因此自定义模型仍需保存配置和补充来源。

`performance_valid=false`、`data_valid=false` 和 `coverage_complete=false` 将结构正确性与硬件真实性分开。测试可以证明公式、图校验和调度契约没有回归，不能证明 RTL 延迟、数值输出或完整模型吞吐。

这种保守声明使 model_eval 适合比较结构、发现资源约束和整理证据缺口，而不适合替代 RTL 校准、逐周期仿真或真实推理 benchmark。
